# 🏠 Proyek Rumah Pintar Mini — versi rujukan

🌐 **Bahasa Indonesia** · [English](../en/mini-smart-home/README.md)

Folder ini berisi **kode proyek benang merah** kurikulum dalam versi terbarunya. Setiap modul menambahkan satu-dua bagian; folder `kode/` di setiap modul menyimpan "potret" pada minggu itu, sedangkan folder ini selalu berisi versi paling baru.

> **Untuk pembelajar:** proyekmu sendiri tinggal di repositori milikmu, `rumah-pintar-mini`, yang dibuat dengan GitHub Desktop di [Modul 3](../fase-0-fondasi/modul-03-cpp-untuk-esp32/README.md#-tambahan-ke-rumah-pintar-mini). Folder ini adalah **kunci jawaban dan rujukan**. Kerangka v0.1.0 (Modul 3), folder `alat/` (Modul 4), dan `PETA-PIN.md` (Modul 5) memang disalin utuh. Mulai Modul 5, isi firmware (dan mulai Modul 16, backend) kamu tulis sendiri dengan panduan di setiap modul — bandingkan dengan milikmu kalau ada yang macet, tetapi jangan menyalinnya mentah-mentah.

## Menjalankan seluruh sistem dalam satu perintah (Modul 26)

Sejak Modul 26, semua layanan pusat menyala bersama dari akar proyek di laptop yang hanya punya Git dan Docker (Docker Desktop di Windows dan macOS, Docker Engine di Linux): tanpa Node.js dan tanpa `npm install`. Langkah lengkapnya, termasuk memindahkan database dan Grafana Modul 17–25 tanpa kehilangan data, ada di [Modul 26](../fase-5-operasi-skala/modul-26-docker-compose/README.md).

1. *Clone* repositorimu, lalu buka terminal di foldernya (akar proyek, tempat `compose.cloud.yml`).
2. Salin `.env.example` menjadi `.env`, isi enam rahasianya (sejak Modul 28 termasuk `MOSQUITTO_DYNSEC_PASSWORD`) dengan teks acak (perintah pembuatnya tertulis di kepala `.env.example`) dan `TOKO_IMAGE`. Di Linux, macOS, dan Pi: `chmod 600 .env`.
3. Laptop baru saja (lemari Modul 17 dan 25 belum ada): `docker volume create rumahpintar-data` dan `docker volume create rumahpintar-grafana-data`. Laptop yang masih menjalankan kontainer lama `rumahpintar-db` dan `rumahpintar-grafana` mengikuti urutan pindahan di Modul 26 Praktik 4 lebih dulu: kontainer lama dihentikan dan dihapus sebelum Compose menyala, lemarinya tetap.
4. `docker compose up -d --wait`. Pertama kali, Compose menarik *image* dari toko *image*, atau membangun *image* backend dan dashboard sendiri kalau belum ada di toko (beberapa menit). Sejak Modul 29, *image* di toko dibangun robot untuk dua jenis prosesor sekaligus (Intel atau AMD = `amd64`, Mac Apple silicon atau Pi = `arm64`), jadi setiap laptop menarik yang cocok tanpa `--build`. *Image* di tokomu masih buatan tangan Modul 26–28 (hanya cocok untuk prosesor pembuatnya), atau kamu sedang mengubah kodenya? Tambahkan `--build` (`docker compose up -d --wait --build`): Compose membangunnya sendiri (lebih lama, butuh unduhan npm). Perintah ini baru selesai sesudah semua layanan siap: layanan panjang tertulis `Healthy`, layanan sekali jalan `Exited`. Periksa dengan `docker compose ps -a` (sekali jalan: `Exited (0)`).
5. Laptop baru: buat akun admin pertama dengan `docker compose exec backend node src/db/kelola-pengguna.ts tambah admin@rumah.test "Admin Rumah" admin` (sandi ditanyakan dua kali). Dashboard ada di **`http://localhost`**, Grafana di **`http://localhost:3000`**.

| Perintah (dari akar proyek) | Gunanya |
| :--- | :--- |
| `docker compose ps -a` | keadaan semua layanan, termasuk layanan sekali jalan yang sudah selesai (`Exited (0)`); tanpa `-a` layanan itu tidak tampil |
| `docker compose logs -f backend` | log satu layanan (juga `mosquitto`, `grafana`, `web`, …); **Ctrl + C** hanya berhenti membaca |

## Di internet (Modul 27)

Sejak [Modul 27](../fase-5-operasi-skala/modul-27-deploy-internet-tls-pwa/README.md), `compose.cloud.yml` yang **sama** berjalan di laptop, di VPS, atau di Pi; yang berbeda hanya isi `.env` (tabel "nilai per tempat" di bagian bawah `.env.example`). Gerbang Pi (`edge/`) meneruskan data perangkat ke pusat lewat jembatan yang menahan pesan selama pusat tak terjangkau. Langkah lengkap, alasan, dan cara memeriksa setiap langkah ada di modulnya; ringkasannya:

**Jalur utama: VPS dengan nama domain dan HTTPS.**

1. Di DNS domainmu: record **A** `iot` dan `mqtt` menunjuk IP VPS ("DNS only", awan abu-abu di Cloudflare). Jangan record AAAA: loket `0.0.0.0` hanya IPv4.
2. Di VPS (pengguna biasa yang boleh memakai Docker): *clone* repositorimu, `cp .env.example .env`, isi rahasia dan kolom **VPS** tabel itu (`DOMAIN_WEB`, `DOMAIN_MQTT`, `KONF_PUSAT=pusat-internet.conf`, `CORS_ORIGIN=https://iot.namaanda.my.id`, `ALAMAT_WEB=0.0.0.0`, `ALAMAT_MQTT=127.0.0.1`, `GRAFANA_ALAMAT`), lalu `chmod 600 .env`.
3. Lemari riwayat: `docker volume create rumahpintar-data` dan `docker volume create rumahpintar-grafana-data` (atau pindahkan riwayat dari laptop seperti di modul), lalu `docker compose up -d --wait`. Modul 27 membangun *image* di VPS dulu (`docker compose build`); sejak Modul 29 VPS menarik *image* buatan robot dengan `sh skrip/pasang.sh` ([Diuji dan dipasang otomatis](#diuji-dan-dipasang-otomatis-modul-29)). Caddy meminta sertifikat Let's Encrypt untuk kedua nama sendiri (`docker compose logs web`: `certificate obtained successfully`), dan layanan sekali jalan `sertifikat-mqtt` menyalin sertifikat `mqtt.` untuk pintu 8883.
4. Pasang baris cron mingguan yang tertulis di kepala [`skrip/perbarui-sertifikat-mqtt.sh`](skrip/perbarui-sertifikat-mqtt.sh) (`crontab -e`), lalu coba skripnya sekali dengan tangan.
5. Buat akun broker `jembatan-pi` di VPS, lalu di Pi pakai blok JALUR UTAMA `edge/jembatan.contoh.conf` (resep di [`edge/README.md`](edge/README.md)).

Yang terbuka di VPS hanya 22 (SSH), 80, 443 (TCP dan UDP), dan 8883; database, Grafana, backend, dan broker polos 1883 tetap `127.0.0.1` (dari laptop lewat terowongan SSH, misalnya `ssh -L 3000:127.0.0.1:3000`).

**Jalur gratis: semua di Pi dengan Cloudflare Tunnel.** `compose.cloud.yml` menyala di Pi yang juga menjalankan gerbang, dengan kolom **Pi** tabel itu (`PORT_MQTT=1884`, `ALAMAT_MQTT=172.17.0.1`, `PROKSI_TEPERCAYA=private_ranges`, `TUNNEL_TOKEN` dari dasbor Cloudflare, `COMPOSE_PROFILES=terowongan`). Jembatan gerbang memakai blok JALUR RUMAH ke `pusat:1884` dengan `ALAMAT_PUSAT=host-gateway` di `edge/.env`. Broker MQTT tidak lewat terowongan.

**Dari kode Modul 26 ke kode Modul 27 (laptop).** `.env` Modul 26 tetap jalan, dengan dua beda yang tidak diperingatkan Compose:

- Broker polos 1883 kini bawaannya `127.0.0.1`. Kit B (jembatan Pi → laptop): tambahkan `ALAMAT_MQTT=0.0.0.0` ke `.env` **sebelum** `docker compose up -d`; tanpa baris itu jembatan tidak tersambung lagi dan dashboard hanya menampilkan data basi.
- Compose juga memesan `127.0.0.1:443` dan `127.0.0.1:8883`. `port is already allocated` saat `up -d` = loket itu sudah dipakai program lain di laptop: ganti `PORT_HTTPS` atau `PORT_MQTTS` di `.env` (misalnya 8443 dan 8884).

Lalu `docker compose up -d --wait`: Compose menarik atau membangun backend 1.4.0 dan dashboard 1.3.0 (`--build` bila prosesor laptop berbeda dengan pembuat image di toko).

## OTA & armada (Modul 28)

Sejak [Modul 28](../fase-5-operasi-skala/modul-28-ota-provisioning-fleet/README.md), Node 1 tidak perlu lagi dicabut dari kotaknya untuk diperbarui: server yang memerintahkannya memasang firmware baru **lewat udara** (OTA), dan firmware baru yang tidak bisa tersambung ke broker dalam 60 detik dibatalkan sendiri oleh papan (*rollback*). Yang baru:

- **Pembaruan lewat udara dan *rollback*** (firmware Node 1 1.7.0): perangkat mengunduh `<alamat server>/fw/node-1/<versi>.bin` lewat rute berkunci (kunci perangkat Modul 21), hanya dari alamat server yang tersimpan di papannya sendiri, lalu harus membuktikan diri dalam masa uji 60 detik.
- **Layar Armada** (dashboard 1.4.0, backend 1.5.0): versi dan kesehatan setiap perangkat, unggah firmware, perbarui satu perangkat, perangkat *canary* dulu, lalu **Perbarui semua**; riwayat pembaruan, jeda `vitals`, dan **Nonaktifkan** untuk perangkat yang hilang.
- **Kode klaim**: papan baru mendaftar sendiri dengan kode sekali pakai buatan admin, tanpa mengetik kunci. Akun brokernya dibuat backend sendiri (*dynamic security*).
- **Node 1 di dalam kotak**: pin tidak berubah; cara menyambungnya ada di [`PETA-PIN.md`](PETA-PIN.md#node-1-di-dalam-kotak-sejak-modul-28) versi 7.

**Urutan pasang: pusat dulu, lalu gerbang, baru firmware.** Backend lama menolak `vitals` firmware baru, dan gerbang tanpa plugin tidak bisa menerima akun perangkat otomatis.

1. **Pusat** (VPS di jalur utama; laptop, atau Pi di jalur gratis): `git pull`, tambahkan `MOSQUITTO_DYNSEC_PASSWORD` (acak, minimal 12 huruf) ke `.env`, lalu salin baris bagian "Armada" dari `.env.example` ke `.env` dan isi: `ALAMAT_SERVER`, alamat yang dipakai perangkat untuk mengunduh firmware (`https://iot.namaanda.my.id` di VPS; `http://<IP Pi>` di Pi jalur gratis, bersama `PINTU_WEB_DALAM=8081`; `http://<IP laptop>` tanpa Pi), dan `AKUN_BROKER_OTOMATIS` (`gerbang:pi1` bila perangkat masuk lewat gerbang Pi, `pusat` bila perangkat masuk langsung ke broker pusat). Bangun dan nyalakan seperti di Modul 27 (`docker compose build`, lalu `docker compose up -d --wait`; sejak Modul 29 cukup `sh skrip/pasang.sh`, tanpa membangun): backend 1.5.0 menerapkan migrasi `011`, dan dashboard 1.4.0 menampilkan menu **Armada**.
2. **Gerbang Pi** (folder `edge`, sesudah `git pull`): `MOSQUITTO_DYNSEC_PASSWORD` ke `edge/.env`, dua baris `topic dynamic-security/…` dari `jembatan.contoh.conf` ke `jembatan/pusat.conf`, lalu `docker compose up -d --force-recreate mosquitto`. Daftarkan perangkat baru **sesudah** langkah ini. Akun perangkat lama Modul 21 dipindah satu per satu: ganti kunci, `kunci <isi>` di Serial Monitor, `mosquitto_passwd -D`, lalu *restart* gerbang.
3. **Firmware Node 1 1.7.0** lewat kabel, sekali saja (Arduino IDE, paket esp32 3.3.12, **Minimal SPIFFS**). Sesudah itu, versi berikutnya diunggah di layar **Armada** dan dikirim lewat udara: perangkat *canary* dulu, **Perbarui semua** sesudah canary berhasil.

Rincian setiap langkah, termasuk jalan mundur ke Modul 27: [`edge/README.md`](edge/README.md#akun-perangkat-otomatis-modul-28) (akun perangkat otomatis), [`backend/README.md`](backend/README.md#pembaruan-firmware-armada-dan-kode-klaim-modul-28) (rute, setelan, Bruno), [`frontend/README.md`](frontend/README.md#armada-modul-28) (layar Armada), [`firmware/README.md`](firmware/README.md) (Node 1 1.7.0, library, membuat berkas `.bin`), [`alat/README.md`](alat/README.md#pembaruan-firmware-tiruan-rollback-tiruan-dan-kode-klaim-modul-28) (perangkat tiruan dan berkas `.bin` tiruan untuk jalur tanpa Kit), [`grafana/README.md`](grafana/README.md) (Batasan: perangkat yang dinonaktifkan), dan [`KONTRAK-DATA.md`](KONTRAK-DATA.md) versi 1.6.

**Keamanan berkas `.bin`.** Berkas firmware Node 1 bisa berisi kunci ESP-NOW dan sandi portal (dari `kunci.h`), jadi:

- Jangan pernah di-*commit*, dibagikan, atau diunggah ke tempat publik: `.gitignore` mengabaikan `*.bin` dan `firmware/**/build/`. Satu-satunya tempat unggahnya adalah **Unggah firmware Node 1** di layar Armada.
- Server menyimpannya di lemari `data-firmware` (hanya dipasang di layanan backend) dan hanya memberikannya lewat rute berkunci `/fw/…` kepada perangkat terdaftar yang menunjukkan kuncinya. Caddy tidak pernah menyajikannya apa adanya.
- Yang diunggah hanya `node-1-rumah.ino.bin` dari folder `build/` sketsa (bukan `.merged.bin` atau `.bootloader.bin`), dan `UJI_KUNCI_SALAH` dikembalikan ke `0` sebelum *commit*.
- Cadangkan akun broker dan berkas firmware dengan `sh skrip/cadangkan-akun-broker.sh` (hasilnya di `backup/`, tidak ikut Git): `docker compose down -v` menghapus keduanya.
- Jalur tanpa Kit memakai berkas **tiruan** dari `alat/buat-bin-tiruan.js`: bukan firmware, jangan di-*flash* ke papan.

## Diuji dan dipasang otomatis (Modul 29)

Sejak [Modul 29](../fase-5-operasi-skala/modul-29-testing-cicd/README.md), setiap perubahan diuji **robot** (GitHub Actions) sebelum boleh masuk `main`, dibungkus menjadi *image* untuk dua jenis prosesor, lalu dipasang sendiri ke VPS dan Pi **tanpa kamu SSH** (robot sendiri tetap masuk ke VPS lewat SSH, dengan kunci khusus). Versi proyek kini **satu nomor**: backend dan dashboard sama-sama **2.0.0**, sama dengan tag *image* di `compose.cloud.yml`, entri teratas [`CHANGELOG.md`](CHANGELOG.md), dan tag Git `v2.0.0` yang dibuat robot. Langkah lengkap, alasan, dan cara memeriksa setiap langkah ada di modulnya; ringkasannya:

| Job robot ([`ci.yml`](.github/workflows/ci.yml)) | Kapan | Yang dikerjakan |
| :--- | :--- | :--- |
| `periksa` | setiap *pull request* ke `main` dan setiap *push* ke `main` | satpam versi (`skrip/cek-versi.mjs`), sakelar uji firmware dan berkas `.bin`; backend `npm run cek`, `npm run lint`, `npm audit --omit=dev --audit-level=high`; frontend `npm run lint`, `npm test`, `npm run cek-skema`, `npm run build`, dan `npm audit` yang sama |
| `uji` | sama, bersamaan dengan `periksa` | migrasi dua kali ke database TimescaleDB uji sekali pakai (kali kedua: `0 migrasi baru diterapkan`), lalu `npm test` backend: 203 *unit test* + 20 *integration test* |
| `bangun` | sesudah keduanya hijau | *image* backend dan web untuk `linux/amd64` dan `linux/arm64` tanpa emulasi. *Pull request*: dibangun saja. *Push* ke `main`: dikirim ke GHCR sebagai `<versi>` dan `sha-<7 huruf>`, kecuali versi itu sudah ada |
| `staging` | *push* ke `main` yang membawa versi baru | gladi resik di mesin robot yang dibuang sesudahnya: `compose.cloud.yml` yang sama, *image* baru, rahasia acak, database kosong, lalu `skrip/uji-asap.sh` |
| `tandai-rilis` | sesudah `staging` lulus | tag beranotasi `v<versi>` berisi catatan versi itu dari `CHANGELOG.md`: "rilis ini boleh dipasang" |
| `pasang-vps` | sesudah tag dibuat, bila **Variables** `VPS_HOST` diisi | SSH ke VPS dengan kunci robot, yang di VPS hanya bisa menjalankan `skrip/pasang.sh` |

Pi tidak dihubungi robot (GitHub tidak bisa mengetuk Pi di balik router rumah): jam weker systemd [`skrip/systemd/rumahpintar-perbarui.timer`](skrip/systemd/rumahpintar-perbarui.timer) menjalankan `skrip/pasang.sh` 5 menit sesudah Pi menyala, lalu setiap 15 menit (ditambah acak 0–60 detik).

**Satu skrip pemasang untuk VPS dan Pi**, [`skrip/pasang.sh`](skrip/pasang.sh), selalu dipanggil `sh skrip/pasang.sh` dari akar proyek: ambil tag rilis terbaru → majukan `main` ke tag itu (`git merge --ff-only`) → `docker compose pull` → `docker compose up -d --no-build --wait` → *restart* broker (atau Grafana) bila berkas yang dibacanya langsung dari repo berubah → [`skrip/uji-asap.sh`](skrip/uji-asap.sh). Yang dipasang dipilih `PASANG_BAGIAN`: `pusat` (bawaan; VPS), `gerbang` (Pi jalur utama: *image* resmi Mosquitto + konfigurasi `edge/`), atau `pusat gerbang` (Pi jalur gratis). Gagal di langkah mana pun = berhenti dengan `GAGAL: …`. Gagal sebelum `up` (misalnya *image* belum bisa ditarik): kontainer lama tetap berjalan, tetapi salinan repo sudah di rilis baru, jadi berkas yang dibaca langsung dari repo (misalnya dashboard Grafana) bisa sudah berganti. Pi mengulang sendiri 15 menit kemudian; VPS mengulang saat robot datang lagi: rilis berikutnya, atau **Re-run failed jobs** pada run yang job `pasang-vps`-nya merah (bukan **Re-run all jobs**: tag rilisnya sudah ada, jadi `pasang-vps` dilewati). Rilis yang berhasil dipasang dicatat di `.git/rumahpintar-terpasang`, jadi putaran tanpa rilis baru hanya menulis `… sudah terpasang (…): tidak ada rilis baru`. Skrip hanya memasang tag yang ada di cabang `main` GitHub: tag di cabang lain diabaikan.

**Sekali saja, berurutan:**

1. Repo `rumah-pintar-mini` **publik** (**Settings** → **General** → **Danger Zone**). Di akun gratis, aturan cabang hanya tersedia untuk repo publik, dan robot di repo publik tidak memotong kuota menit.
2. *Pull request* pertama yang membawa `ci.yml` di-*merge* dulu (sebuah *check* baru bisa diwajibkan sesudah pernah berjalan). Lalu **Settings** → **Branches** → aturan klasik untuk `main`: **Require a pull request before merging** (persetujuan 0), **Require status checks to pass before merging** dengan `periksa`, `uji`, dan `bangun`, **Require branches to be up to date before merging**, dan **Do not allow bypassing the above settings**. Tanpa kotak terakhir, kamu sebagai pemilik repo tetap bisa *merge* *pull request* yang merah.
3. Sesudah robot pertama kali mengirim `2.0.0`, jadikan paket `rumah-pintar-mini-backend` dan `rumah-pintar-mini-web` di GHCR **publik** (halaman paket → **Package settings** → **Change visibility**). Paket publik tidak bisa diprivatkan lagi, jadi periksa dulu `docker history --no-trunc`. Bukti dari laptop tanpa *login*: `docker pull ghcr.io/<akun>/rumah-pintar-mini-backend:2.0.0` berhasil, dan `docker buildx imagetools inspect ghcr.io/<akun>/rumah-pintar-mini-backend:2.0.0` menulis `linux/amd64` dan `linux/arm64`.
4. **VPS** (jalur utama), terakhir kali lewat SSH tangan untuk memasang: `git pull`, pastikan `TOKO_IMAGE` di `.env` = `ghcr.io/<akun huruf kecil>`, lalu `sh skrip/pasang.sh` (2.0.0 **ditarik**, tidak dibangun). Urutan ini penting: tanpa `git pull` lebih dulu, `skrip/pasang.sh` belum ada di VPS dan robot gagal dengan `cannot open /home/rumah/rumah-pintar-mini/skrip/pasang.sh`. (Pembaruan dari rilis sesudah 2.0.0: kalau `git pull` tangan itu ikut mengubah `edge/acl-broker`, `edge/pusat*.conf`, atau `grafana/provisioning/`, restart layanannya sekali dengan tangan, `docker compose restart mosquitto` atau `grafana`; pemasangan pertama lewat skrip tidak tahu apa yang sudah berubah sebelumnya.) Buat kunci robot di laptop: `ssh-keygen -t ed25519 -f ~/.ssh/robot_rumah -N "" -C robot-pasang` (tanpa frasa sandi, karena robot tidak bisa mengetiknya). Baris kunci publiknya (`~/.ssh/robot_rumah.pub`) ditambahkan ke `~/.ssh/authorized_keys` pengguna `rumah` di VPS **dengan awalan pembatas**:

   ```text
   restrict,command="sh /home/rumah/rumah-pintar-mini/skrip/pasang.sh" ssh-ed25519 AAAA… robot-pasang
   ```

   Dengan awalan itu, kunci ini hanya bisa menjalankan `skrip/pasang.sh`, apa pun perintah yang dikirim, tanpa terminal dan tanpa terowongan. Tulis barisnya sendiri (`nano ~/.ssh/authorized_keys`); **jangan** memakai `ssh-copy-id` untuk kunci robot, karena perintah itu menambahkan kunci TANPA awalan pembatas. Buktikan pembatasnya aktif dari laptop: `ssh -i ~/.ssh/robot_rumah rumah@<alamat VPS> whoami` harus menjawab dengan baris `pasang.sh` (misalnya `… sudah terpasang (pusat): tidak ada rilis baru`), **bukan** `rumah`. Robot pun memeriksanya: ia mengirim kata penanda `kunci-robot-belum-dibatasi-command`, yang diabaikan VPS bila awalan `command=` ada, dan menjadi `command not found` (job `pasang-vps` merah) bila awalan itu lupa ditulis. Lalu di GitHub (**Settings** → **Secrets and variables** → **Actions**): **Secrets** `VPS_KUNCI_SSH` (isi berkas kunci privat `~/.ssh/robot_rumah`), **Variables** `VPS_HOST` (alamat VPS), `VPS_USER` (kosong = `rumah`), dan `VPS_KNOWN_HOSTS` (hasil `ssh-keyscan -t ed25519 <alamat VPS>`, sesudah sidiknya, `ssh-keyscan -t ed25519 <alamat VPS> | ssh-keygen -lf -`, kamu cocokkan dengan `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` di VPS).
5. **Pi**: `git pull` sekali dengan tangan (Pi jalur gratis juga `TOKO_IMAGE` di `.env` dan `PASANG_BAGIAN="pusat gerbang" sh skrip/pasang.sh` sekali), lalu pasang jam wekernya. Salin dulu kedua berkas unit ke `/etc/systemd/system/`, lalu sesuaikan `User=`, jalur, dan `PASANG_BAGIAN` di **salinannya**, bukan di berkas repo (berkas repo yang disunting membuat `pasang.sh` berhenti). Perintah pemasangannya tertulis di kepala [`skrip/systemd/rumahpintar-perbarui.service`](skrip/systemd/rumahpintar-perbarui.service), dan resepnya di [`edge/README.md`](edge/README.md#pi-memperbarui-dirinya-sendiri-modul-29).

**Setiap perubahan sesudahnya**: cabang baru → ubah → naikkan versi bila yang dipasang berubah → *pull request* → **Checks** hijau → **Merge**. Robot memasang ke VPS beberapa menit kemudian; Pi menyusul, biasanya paling lambat ±17 menit sesudah tag rilisnya dibuat (15 menit + acak sampai 1 menit + ketelitian jam weker sampai 1 menit), ditambah lama menarik *image*. Periksa tanpa SSH: nomor versi di bawah judul layar **Masuk** di `https://<domainmu>` (muat ulang **dua kali**, karena PWA) dan `"versi":"…"` di `https://<domainmu>/api/health`.

**Versi.** Kalau yang dipasang di VPS atau Pi berubah, versi wajib naik (SemVer: PATCH untuk perbaikan, MINOR untuk fitur baru, MAYOR bila pemakai lama terpaksa ikut berubah). "Yang dipasang" = isi *image* backend dan web, `compose.cloud.yml`, konfigurasi broker di `edge/` (`compose.edge.yml`, `gerbang.conf`, `pusat.conf`, `pusat-internet.conf`, `acl-broker`), `grafana/provisioning/`, `grafana/dashboards/`, `grafana/pengguna-grafana.sql`, dan `skrip/*.sh`; dokumen (`*.md`), tes, Bruno, dan berkas robot tidak. Tanpa versi baru, robot tidak membuat rilis, dan perubahan itu tidak pernah sampai ke VPS dan Pi. Naikkan di semua tempat sekaligus:

```bash
cd backend && npm version 2.0.1 --no-git-tag-version && cd ..
cd frontend && npm version 2.0.1 --no-git-tag-version && cd ..
```

lalu tiga baris `image:` di `compose.cloud.yml` dan entri `## [2.0.1] - <tanggal>` di `CHANGELOG.md` (di bawah `## [Belum Dirilis]`). Periksa sebelum *push*: `git fetch`, lalu `BASIS=origin/main node skrip/cek-versi.mjs` (PowerShell: `$env:BASIS = "origin/main"; node skrip/cek-versi.mjs`) harus menulis `LULUS`.

**Kembali ke versi sebelumnya = maju.** Tombol **Revert** di *pull request* yang bermasalah membuat *pull request* baru berisi isi lama; nomornya tetap NAIK (misalnya `2.0.2` berisi isi `2.0.0`) dengan entri `Diperbaiki: mengembalikan …`, lalu robot memasangnya seperti biasa. Karena itu migrasi database hanya boleh menambah (tabel, kolom, atau indeks baru): *image* bisa mundur, database tidak. Memasang tag lama dengan tangan adalah langkah darurat (*runbook*, Modul 30).

**Jangan** menyunting berkas langsung di VPS atau Pi (skrip berhenti dengan `ada berkas yang disunting langsung di mesin ini`; ubah lewat *pull request*), `git pull` tangan di sana sesudah peralihan (skrip menunggu sampai versi itu dirilis), `chmod +x` skripnya (Git menganggapnya suntingan), atau `sudo sh skrip/pasang.sh` (skrip menolak root; Docker menolak tanpa `sudo`? keluar dari SSH lalu masuk lagi supaya grup `docker` berlaku). **Jangan** juga membuat, memindah, atau menghapus tag `v…` sendiri, termasuk lewat tombol **Releases** → **Draft a new release**: tag rilis hanya buatan robot, sesudah lulus uji dan *staging*. Skrip tidak pernah menjalankan `docker compose down -v`, `prune`, atau `git reset --hard`. *Image* lama menumpuk di VPS dan Pi; membereskannya dibahas di Modul 30. Menghentikan otomatisasi sementara (misalnya saat memperbaiki sesuatu dengan tangan): di Pi `sudo systemctl disable --now rumahpintar-perbarui.timer`, untuk VPS kosongkan **Variables** `VPS_HOST`.

**Jalur lain.** Jalur gratis (semua di Pi + Cloudflare Tunnel): `VPS_HOST` dibiarkan kosong (job `pasang-vps` dilewati), dan timer Pi memakai `PASANG_BAGIAN=pusat gerbang`. Tanpa Pi: langkah 5 dilewati. Repo privat: aturan cabang tidak tersedia di akun gratis, robot memotong kuota menit bulanan, dan VPS serta Pi butuh token baca GHCR **dan** kunci baca repo (*deploy key*) untuk `git fetch`; rinciannya di modul.

**Batas jujur (lab penulis, 4 November 2026, tanpa akun GitHub):** `ci.yml` dijalankan apa adanya, langkah `run:` dan `uses:` (*action* resmi diunduh dari github.com tanpa akun), oleh *forge* dan *runner* tiruan (Gitea 28.2.0 + Gitea Runner 5.2.4) di Raspberry Pi 5 penulis. GHCR diganti toko *image* lokal; Docker robot, VPS, dan dua Pi (jalur utama dan jalur gratis) diganti kontainer Docker-in-Docker `--privileged` di mesin yang sama (diizinkan khusus untuk lab itu, lalu dihapus). `pasang-vps` masuk ke VPS tiruan lewat SSH sungguhan dengan kunci `restrict,command=`, dan `skrip/pasang.sh` memasang 2.0.1, 2.0.2, dan 2.0.4 di sana dengan Docker sungguhan (2.0.0 dengan tangan); job itu merah tepat pada tiga kesalahan sengaja: sidik host salah, kunci salah, dan awalan `command=` lupa. Kedua Pi tiruan memasang 2.0.0 dengan tangan, lalu rilis berikutnya sendiri lewat `skrip/pasang.sh` (`PASANG_BAGIAN=gerbang`; jalur gratis `pusat gerbang`), dibangunkan penjadwal tiruan tiap ±1 menit, bukan systemd. Belum diuji penulis: akun GitHub dan GHCR sungguhan (izin token, antrean `concurrency`, aturan cabang, paket publik: menurut dokumen GitHub), jam weker systemd yang sungguh berjalan (kontainer lab tanpa systemd sebagai PID 1: kedua berkas unit hanya diperiksa `systemd-analyze verify`), uji asap untuk VPS ber-domain, *image* amd64 di mesin amd64, membangun lewat emulasi QEMU (robot membangun tanpa emulasi), dan Playwright. Waktu *merge* → VPS ±5–6½ menit = contoh lab dengan robot tiruan di Raspberry Pi 5 dan *image* dasar yang sudah ada di mesin itu; robot GitHub masih harus menarik ±1,1 GB di job `staging`.
