# 🏠 Mini Smart Home project — reference version

🌐 **English** · [Bahasa Indonesia](../../../../fase-5-operasi-skala/modul-29-testing-cicd/kode/README.md)

This folder holds the curriculum's **running-project code** in its latest version. Every module adds one or two parts; the `code/` folder of each module keeps a "snapshot" of that week, while this folder always holds the newest version.

> **For learners:** your own project lives in your own repository, `mini-smart-home`, which you create with GitHub Desktop in [Module 3](../../../phase-0-foundations/module-03-cpp-for-esp32/README.md#-add-on-to-mini-smart-home). This folder is the **answer key and reference**. The v0.1.0 skeleton (Module 3), the `tools/` folder (Module 4), and `PIN-MAP.md` (Module 5) are meant to be copied as they are. From Module 5 on, you write the firmware (and from Module 16 on, the backend) yourself with the guidance in each module — compare it with yours if you get stuck, but don't copy it blindly.

## How to run the whole system with one command (Module 26)

Since Module 26, every central service starts together from the project root on a laptop that only has Git and Docker (Docker Desktop on Windows and macOS, Docker Engine on Linux): no Node.js and no `npm install`. The full steps, including moving the Module 17–25 database and Grafana without losing data, are in [Module 26](../../module-26-docker-compose/README.md).

1. Clone your repository, then open a terminal in its folder (the project root, where `compose.cloud.yml` is).
2. Copy `.env.example` to `.env`, fill in its six secrets (since Module 28 including `MOSQUITTO_DYNSEC_PASSWORD`) with random text (the command that makes it is written in the header of `.env.example`) and `IMAGE_REGISTRY`. On Linux, macOS, and the Pi: `chmod 600 .env`.
3. New laptop only (the Module 17 and 25 cupboards don't exist yet): `docker volume create smarthome-data` and `docker volume create smarthome-grafana-data`. A laptop that still runs the old `smarthome-db` and `smarthome-grafana` containers follows the order of the move in Module 26 Practice 4 first: the old containers are stopped and removed before Compose starts, their cupboards stay.
4. `docker compose up -d --wait`. The first time, Compose pulls the images from the image shop, or builds the backend and dashboard images itself when the shop doesn't have them yet (a few minutes). Since Module 29, the images in the shop are built by the robot for two kinds of processor at once (Intel or AMD = `amd64`, an Apple silicon Mac or a Pi = `arm64`), so every laptop pulls the one that fits without `--build`. Are the images in your shop still the hand-made ones of Modules 26–28 (they only fit the processor of their maker), or are you changing the code? Add `--build` (`docker compose up -d --wait --build`): Compose builds them itself (slower, needs npm downloads). This command only finishes after every service is ready: long-running services show `Healthy`, one-off services `Exited`. Check with `docker compose ps -a` (one-off: `Exited (0)`).
5. New laptop: make the first admin account with `docker compose exec backend node src/db/manage-users.ts add admin@home.test "Home Admin" admin` (the password is asked twice). The dashboard is at **`http://localhost`**, Grafana at **`http://localhost:3000`**.

| Command (from the project root) | What it does |
| :--- | :--- |
| `docker compose ps -a` | the state of every service, including one-off services that are done (`Exited (0)`); without `-a` those services don't show |
| `docker compose logs -f backend` | the log of one service (also `mosquitto`, `grafana`, `web`, …); **Ctrl + C** only stops reading |
| `docker compose down` then `docker compose up -d` | stops and starts the whole home again; the history stays (prove it with [`scripts/fingerprint.sql`](scripts/fingerprint.sql)) |
| `docker compose stop mosquitto`, then `docker compose start mosquitto` | with `MQTT_ADDRESS=0.0.0.0` (Kit B), the central broker listens on every interface of the laptop and starts every time Docker starts: stop it before the laptop joins a public Wi-Fi (a café, a campus), start it again at home. The default since Module 27 (`127.0.0.1`) can't be seen from the Wi-Fi |

**Never** `docker compose down -v` (it deletes the cupboard of the broker password file), and never `docker volume rm` or `prune` for the `smarthome-data` and `smarthome-grafana-data` cupboards: without a backup, your history is gone. `.env` and the output of `docker compose config` hold every secret: don't paste them into a forum, an issue, or an AI. The details of each service are in `backend/README.md`, `frontend/README.md`, `grafana/README.md`, and `edge/README.md`.

## On the internet (Module 27)

Since [Module 27](../../module-27-deploy-internet-tls-pwa/README.md), the **same** `compose.cloud.yml` runs on the laptop, on a VPS, or on the Pi; only the contents of `.env` differ (the "values per place" table at the bottom of `.env.example`). The Pi gateway (`edge/`) forwards the device data to the center through a bridge that holds messages while the center can't be reached. The full steps, the reasons, and how to check every step are in the module; in short:

**The main path: a VPS with a domain name and HTTPS.**

1. In your domain's DNS: **A** records `iot` and `mqtt` pointing at the VPS IP ("DNS only", the gray cloud in Cloudflare). No AAAA record: the `0.0.0.0` counters are IPv4 only.
2. On the VPS (as a regular user allowed to use Docker): clone your repository, `cp .env.example .env`, fill in the secrets and the **VPS** column of that table (`WEB_DOMAIN`, `MQTT_DOMAIN`, `CENTER_CONF=center-internet.conf`, `CORS_ORIGIN=https://iot.yourname.my.id`, `WEB_ADDRESS=0.0.0.0`, `MQTT_ADDRESS=127.0.0.1`, `GRAFANA_URL`), then `chmod 600 .env`.
3. The history cupboards: `docker volume create smarthome-data` and `docker volume create smarthome-grafana-data` (or move the history from the laptop as in the module), then `docker compose up -d --wait`. Module 27 built the images on the VPS first (`docker compose build`); since Module 29 the VPS pulls the robot's images with `sh scripts/deploy.sh` ([Tested and deployed automatically](#tested-and-deployed-automatically-module-29)). Caddy asks Let's Encrypt for certificates for both names by itself (`docker compose logs web`: `certificate obtained successfully`), and the one-off service `mqtt-certificate` copies the `mqtt.` certificate for door 8883.
4. Install the weekly cron line written in the header of [`scripts/renew-mqtt-certificate.sh`](scripts/renew-mqtt-certificate.sh) (`crontab -e`), then try the script once by hand.
5. Make the broker account `pi-bridge` on the VPS, then on the Pi use the MAIN PATH block of `edge/bridge.example.conf` (the recipe is in [`edge/README.md`](edge/README.md)).

Only 22 (SSH), 80, 443 (TCP and UDP), and 8883 are open on the VPS; the database, Grafana, the backend, and the plain broker 1883 stay on `127.0.0.1` (from the laptop through an SSH tunnel, for example `ssh -L 3000:127.0.0.1:3000`).

**The free path: everything on the Pi with Cloudflare Tunnel.** `compose.cloud.yml` runs on the Pi that also runs the gateway, with the **Pi** column of that table (`PORT_MQTT=1884`, `MQTT_ADDRESS=172.17.0.1`, `CADDY_TRUSTED_PROXIES=private_ranges`, `TUNNEL_TOKEN` from the Cloudflare dashboard, `COMPOSE_PROFILES=tunnel`). The gateway bridge uses the HOME PATH block to `center:1884` with `CENTER_ADDRESS=host-gateway` in `edge/.env`. The MQTT broker doesn't go through the tunnel.

**From the Module 26 code to the Module 27 code (laptop).** The Module 26 `.env` still works, with two differences Compose doesn't warn about:

- The plain broker 1883 now defaults to `127.0.0.1`. Kit B (the Pi → laptop bridge): add `MQTT_ADDRESS=0.0.0.0` to `.env` **before** `docker compose up -d`; without that line the bridge doesn't connect again and the dashboard only shows stale data.
- Compose also reserves `127.0.0.1:443` and `127.0.0.1:8883`. `port is already allocated` at `up -d` = another program on the laptop already uses that counter: change `PORT_HTTPS` or `PORT_MQTTS` in `.env` (for example 8443 and 8884).

Then `docker compose up -d --wait`: Compose pulls or builds backend 1.4.0 and dashboard 1.3.0 (`--build` if the laptop's processor differs from the one that made the image in the shop).

## OTA & fleet (Module 28)

Since [Module 28](../../module-28-ota-provisioning-fleet/README.md), Node 1 no longer has to be taken out of its box to be updated: it's the server that orders it to install new firmware **over the air** (OTA), and new firmware that can't connect to the broker within 60 seconds is cancelled by the board itself (rollback). What's new:

- **Over-the-air updates and rollback** (Node 1 firmware 1.7.0): the device downloads `<server address>/fw/node-1/<version>.bin` through a locked route (the Module 21 device key), only from the server address stored on its own board, then must prove itself in a 60-second trial period.
- **The Fleet screen** (dashboard 1.4.0, backend 1.5.0): the version and health of every device, uploading firmware, updating one device, the canary devices first, then **Update all**; the update history, the `vitals` interval, and **Deactivate** for a lost device.
- **Claim codes**: a new board registers itself with a single-use code made by the admin, without typing a key. Its broker account is made by the backend itself (dynamic security).
- **Node 1 inside the box**: the pins don't change; how to connect it is in [`PIN-MAP.md`](../../../mini-smart-home/PIN-MAP.md#node-1-inside-the-box-since-module-28) version 7.

**The install order: the center first, then the gateway, only then the firmware.** The old backend refuses the `vitals` of the new firmware, and a gateway without the plugin can't accept automatic device accounts.

1. **The center** (the VPS on the main path; the laptop, or the Pi on the free path): `git pull`, add `MOSQUITTO_DYNSEC_PASSWORD` (random, at least 12 characters) to `.env`, then copy the lines of the "Fleet" section from `.env.example` into `.env` and fill them in: `SERVER_URL`, the address the devices use to download firmware (`https://iot.yourname.my.id` on the VPS; `http://<Pi IP>` on the free-path Pi, together with `WEB_INNER_PORT=8081`; `http://<laptop IP>` without a Pi), and `AUTO_BROKER_ACCOUNTS` (`gateway:pi1` if the devices connect through the Pi gateway, `center` if the devices connect straight to the central broker). Build and start as in Module 27 (`docker compose build`, then `docker compose up -d --wait`; since Module 29 `sh scripts/deploy.sh` is enough, without building): backend 1.5.0 applies the migration `011`, and dashboard 1.4.0 shows the **Fleet** menu.
2. **The Pi gateway** (the `edge` folder, after `git pull`): `MOSQUITTO_DYNSEC_PASSWORD` into `edge/.env`, the two `topic dynamic-security/…` lines from `bridge.example.conf` into `bridge/center.conf`, then `docker compose up -d --force-recreate mosquitto`. Register new devices **after** this step. The old Module 21 device accounts are moved one at a time: rotate the key, `key <value>` in the Serial Monitor, `mosquitto_passwd -D`, then restart the gateway.
3. **Node 1 firmware 1.7.0** by cable, only once (Arduino IDE, the esp32 3.3.12 package, **Minimal SPIFFS**). After that, the next versions are uploaded on the **Fleet** screen and sent over the air: the canary devices first, **Update all** after the canary has succeeded.

The details of every step, including going back to Module 27: [`edge/README.md`](edge/README.md#automatic-device-accounts-module-28) (automatic device accounts), [`backend/README.md`](backend/README.md#firmware-updates-the-fleet-and-claim-codes-module-28) (routes, settings, Bruno), [`frontend/README.md`](frontend/README.md#the-fleet-screen-module-28) (the Fleet screen), [`firmware/README.md`](../../../mini-smart-home/firmware/README.md) (Node 1 1.7.0, libraries, making the `.bin` file), [`tools/README.md`](../../../mini-smart-home/tools/README.md#simulated-firmware-updates-simulated-rollback-and-claim-codes-module-28) (simulated devices and fake `.bin` files for the path without a Kit), [`grafana/README.md`](../../../mini-smart-home/grafana/README.md) (Limits: deactivated devices), and [`DATA-CONTRACT.md`](../../../mini-smart-home/DATA-CONTRACT.md) version 1.6.

**Keeping `.bin` files safe.** A Node 1 firmware file may contain the ESP-NOW key and the portal password (from `keys.h`), so:

- Never commit it, share it, or upload it to a public place: `.gitignore` ignores `*.bin` and `firmware/**/build/`. The only place to upload it is **Upload Node 1 firmware** on the Fleet screen.
- The server keeps it in the `firmware-data` cupboard (only mounted in the backend service) and only gives it out through the locked route `/fw/…` to a registered device that shows its key. Caddy never serves it as it is.
- Only `node-1-home.ino.bin` from the sketch's `build/` folder is uploaded (not `.merged.bin` or `.bootloader.bin`), and `TEST_WRONG_KEY` is set back to `0` before a commit.
- Back up the broker accounts and the firmware files with `sh scripts/backup-broker-accounts.sh` (the result goes to `backup/`, not into Git): `docker compose down -v` deletes both.
- The path without a Kit uses **fake** files from `tools/make-fake-bin.js`: not firmware, don't flash them onto a board.

## Tested and deployed automatically (Module 29)

Since [Module 29](../README.md), every change is tested by the **robot** (GitHub Actions) before it may enter `main`, packed into images for two kinds of processor, then deployed by itself to the VPS and the Pi **without you SSHing in** (the robot itself still logs in to the VPS over SSH, with a special key). The project version is now **one number**: the backend and the dashboard are both **2.0.0**, the same as the image tags in `compose.cloud.yml`, the top entry of [`CHANGELOG.md`](CHANGELOG.md), and the Git tag `v2.0.0` the robot makes. The full steps, the reasons, and how to check every step are in the module; the summary:

| Robot job ([`ci.yml`](.github/workflows/ci.yml)) | When | What it does |
| :--- | :--- | :--- |
| `verify` | every pull request to `main` and every push to `main` | the version guard (`scripts/check-version.mjs`), the firmware test switch and `.bin` files; backend `npm run check`, `npm run lint`, `npm audit --omit=dev --audit-level=high`; frontend `npm run lint`, `npm test`, `npm run check-schema`, `npm run build`, and the same `npm audit` |
| `test` | the same, at the same time as `verify` | the migration twice into a throw-away TimescaleDB test database (the second time: `0 new migration(s) applied`), then the backend `npm test`: 203 unit tests + 20 integration tests |
| `build` | after both are green | the backend and web images for `linux/amd64` and `linux/arm64` without emulation. Pull request: only built. Push to `main`: pushed to GHCR as `<version>` and `sha-<7 characters>`, unless that version already exists |
| `staging` | a push to `main` that brings a new version | a dress rehearsal on the robot's machine that is thrown away afterwards: the same `compose.cloud.yml`, the new images, random secrets, an empty database, then `scripts/smoke-test.sh` |
| `tag-release` | after `staging` passes | the annotated tag `v<version>` holding that version's notes from `CHANGELOG.md`: "this release may be deployed" |
| `deploy-vps` | after the tag is made, when `VPS_HOST` under **Variables** is filled in | SSH to the VPS with the robot key, which on the VPS can only run `scripts/deploy.sh` |

The robot doesn't contact the Pi (GitHub can't knock on a Pi behind the home router): the systemd alarm clock [`scripts/systemd/smarthome-update.timer`](scripts/systemd/smarthome-update.timer) runs `scripts/deploy.sh` 5 minutes after the Pi starts, then every 15 minutes (plus a random 0–60 seconds).

**One deploy script for the VPS and the Pi**, [`scripts/deploy.sh`](scripts/deploy.sh), always called as `sh scripts/deploy.sh` from the project root: fetch the latest release tag → move `main` forward to that tag (`git merge --ff-only`) → `docker compose pull` → `docker compose up -d --no-build --wait` → restart the broker (or Grafana) when a file it reads straight from the repo changed → [`scripts/smoke-test.sh`](scripts/smoke-test.sh). What gets deployed is chosen by `DEPLOY_PARTS`: `center` (the default; the VPS), `gateway` (the main-path Pi: the official Mosquitto image + the `edge/` configuration), or `center gateway` (the free-path Pi). A failure at any step = stop with `FAIL: …`. A failure before `up` (for example the images can't be pulled yet): the old containers keep running, but the repo copy is already on the new release, so files read straight from the repo (for example the Grafana dashboards) may have changed already. The Pi tries again by itself 15 minutes later; the VPS tries again when the robot comes back: the next release, or **Re-run failed jobs** on the run whose job `deploy-vps` is red (not **Re-run all jobs**: its release tag already exists, so `deploy-vps` is skipped). A release deployed successfully is recorded in `.git/smarthome-deployed`, so a round without a new release only writes `… already deployed (…): no new release`. The script only deploys tags on the `main` branch on GitHub: tags on other branches are ignored.

**Once only, in order:**

1. Make the `mini-smart-home` repo **public** (**Settings** → **General** → **Danger Zone**). On a free account, branch rules are only available for public repos, and the robot in a public repo doesn't count against the minutes quota.
2. The first pull request that brings `ci.yml` is merged first (a check can only be required after it has run once). Then **Settings** → **Branches** → a classic rule for `main`: **Require a pull request before merging** (0 approvals), **Require status checks to pass before merging** with `verify`, `test`, and `build`, **Require branches to be up to date before merging**, and **Do not allow bypassing the above settings**. Without the last box, you as the repo owner can still merge a red pull request.
3. After the robot first pushes `2.0.0`, make the packages `mini-smart-home-backend` and `mini-smart-home-web` on GHCR **public** (the package page → **Package settings** → **Change visibility**). A public package can't be made private again, so check `docker history --no-trunc` first. The proof from a laptop without a login: `docker pull ghcr.io/<account>/mini-smart-home-backend:2.0.0` succeeds, and `docker buildx imagetools inspect ghcr.io/<account>/mini-smart-home-backend:2.0.0` writes `linux/amd64` and `linux/arm64`.
4. **VPS** (the main path), the last deployment by hand over SSH: `git pull`, make sure `IMAGE_REGISTRY` in `.env` = `ghcr.io/<account in lowercase>`, then `sh scripts/deploy.sh` (2.0.0 is **pulled**, not built). This order matters: without `git pull` first, `scripts/deploy.sh` isn't on the VPS yet and the robot fails with `cannot open /home/house/mini-smart-home/scripts/deploy.sh`. (Updating from a release after 2.0.0: if that manual `git pull` also changes `edge/acl-broker`, `edge/center*.conf`, or `grafana/provisioning/`, restart its service once by hand, `docker compose restart mosquitto` or `grafana`; the first deployment through the script doesn't know what changed before it.) Make the robot key on the laptop: `ssh-keygen -t ed25519 -f ~/.ssh/robot_house -N "" -C robot-deploy` (without a passphrase, because the robot can't type it). Its public key line (`~/.ssh/robot_house.pub`) is added to `~/.ssh/authorized_keys` of the user `house` on the VPS **with the restricting prefix**:

   ```text
   restrict,command="sh /home/house/mini-smart-home/scripts/deploy.sh" ssh-ed25519 AAAA… robot-deploy
   ```

   With that prefix, this key can only run `scripts/deploy.sh`, whatever command is sent, without a terminal and without a tunnel. Write the line yourself (`nano ~/.ssh/authorized_keys`); **don't** use `ssh-copy-id` for the robot key, because that command adds the key WITHOUT the restricting prefix. Prove from the laptop that the restriction is active: `ssh -i ~/.ssh/robot_house house@<VPS address> whoami` must answer with a `deploy.sh` line (for example `… already deployed (center): no new release`), **not** `house`. The robot checks it too: it sends the marker word `robot-key-not-restricted-by-command`, which the VPS ignores when the `command=` prefix is there, and which becomes `command not found` (the job `deploy-vps` red) when that prefix was forgotten. Then on GitHub (**Settings** → **Secrets and variables** → **Actions**): **Secrets** `VPS_SSH_KEY` (the content of the private key file `~/.ssh/robot_house`), **Variables** `VPS_HOST` (the VPS address), `VPS_USER` (empty = `house`), and `VPS_KNOWN_HOSTS` (the result of `ssh-keyscan -t ed25519 <VPS address>`, after you have compared its fingerprint, `ssh-keyscan -t ed25519 <VPS address> | ssh-keygen -lf -`, with `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the VPS).
5. **Pi**: `git pull` once by hand (on the free-path Pi also `IMAGE_REGISTRY` in `.env` and `DEPLOY_PARTS="center gateway" sh scripts/deploy.sh` once), then install its alarm clock. First copy both unit files to `/etc/systemd/system/`, then adjust `User=`, the paths, and `DEPLOY_PARTS` in the **copies**, not in the repo file (an edited repo file makes `deploy.sh` stop). The install commands are written in the header of [`scripts/systemd/smarthome-update.service`](scripts/systemd/smarthome-update.service), and the recipe in [`edge/README.md`](edge/README.md#the-pi-updates-itself-module-29).

**Every change after that**: a new branch → change → raise the version when what gets deployed changed → pull request → **Checks** green → **Merge**. The robot deploys to the VPS a few minutes later; the Pi follows, usually at most ±17 minutes after its release tag is made (15 minutes + a random delay up to 1 minute + the alarm clock's accuracy up to 1 minute), plus the time to pull the images. Check without SSH: the version number under the title of the **Login** screen at `https://<your domain>` (reload **twice**, because of the PWA) and `"version":"…"` at `https://<your domain>/api/health`.

**Versions.** When what gets deployed to the VPS or the Pi changed, the version must go up (SemVer: PATCH for a fix, MINOR for a new feature, MAJOR when old users are forced to change too). "What gets deployed" = the content of the backend and web images, `compose.cloud.yml`, the broker configuration in `edge/` (`compose.edge.yml`, `gateway.conf`, `center.conf`, `center-internet.conf`, `acl-broker`), `grafana/provisioning/`, `grafana/dashboards/`, `grafana/grafana-user.sql`, and `scripts/*.sh`; documents (`*.md`), tests, Bruno, and the robot's files don't count. Without a new version, the robot makes no release, and that change never reaches the VPS and the Pi. Raise it in every place at once:

```bash
cd backend && npm version 2.0.1 --no-git-tag-version && cd ..
cd frontend && npm version 2.0.1 --no-git-tag-version && cd ..
```

then the three `image:` lines in `compose.cloud.yml` and the entry `## [2.0.1] - <date>` in `CHANGELOG.md` (under `## [Unreleased]`). Check before the push: `git fetch`, then `BASE=origin/main node scripts/check-version.mjs` (PowerShell: `$env:BASE = "origin/main"; node scripts/check-version.mjs`) must write `PASS`.

**Going back to the previous version = going forward.** The **Revert** button on the troublesome pull request makes a new pull request holding the old content; its number still goes UP (for example `2.0.2` holding the content of `2.0.0`) with the entry `Fixed: restores …`, then the robot deploys it as usual. That's why database migrations may only add (new tables, columns, or indexes): an image can go back, a database can't. Deploying an old tag by hand is an emergency step (a runbook, Module 30).

**Don't** edit files directly on the VPS or the Pi (the script stops with `files were edited directly on this machine`; change them through a pull request), run a manual `git pull` there after the switch (the script waits until that version is released), `chmod +x` the scripts (Git sees that as an edit), or `sudo sh scripts/deploy.sh` (the script refuses root; Docker refuses without `sudo`? log out of SSH and in again so the `docker` group applies). **Don't** make, move, or delete a `v…` tag yourself either, not even through the **Releases** → **Draft a new release** button: release tags are only made by the robot, after the tests and staging passed. The script never runs `docker compose down -v`, `prune`, or `git reset --hard`. Old images pile up on the VPS and the Pi; cleaning them up comes in Module 30. To pause the automation (for example while fixing something by hand): on the Pi `sudo systemctl disable --now smarthome-update.timer`, and for the VPS, empty `VPS_HOST` under **Variables**.

**Other paths.** The free path (everything on the Pi + Cloudflare Tunnel): `VPS_HOST` stays empty (the job `deploy-vps` is skipped), and the Pi timer uses `DEPLOY_PARTS=center gateway`. Without a Pi: step 5 is skipped. A private repo: branch rules aren't available on a free account, the robot's runs count against the monthly minutes quota, and the VPS and the Pi need a GHCR read token **and** a repo read key (a deploy key) for `git fetch`; the details are in the module.
