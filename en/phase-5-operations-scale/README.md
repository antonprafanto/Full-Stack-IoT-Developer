## 🎯 Phase 5 completion criteria

This last phase closes with a final project. Before you call yourself a Fullstack IoT Developer 🎓, make sure this evidence is in your GitHub repository ([Syllabus §8](../SYLLABUS.md#8-evaluation--completion-criteria-for-each-phase)):

1. The quiz of every module (5 questions): **at least 4 correct**, for Modules 26–30.
2. **Checkpoint project:** an online system + TLS + OTA + CI/CD + monitoring + capstone.
3. **Artifacts:** a product README + a runbook + a 3-minute demo video.

Module 26 opens this phase: the whole Mini Smart Home is **wrapped in Docker** and starts with one command. Backend 1.3.0 and dashboard 1.2.0 now have two-stage molds (images); the dashboard is served by Caddy at `http://localhost` without Vite, and F5 is safe at every address. One file, `compose.cloud.yml`, starts the database, the central broker, the backend, the web service, and Grafana with `docker compose up -d`, plus three one-off services that prepare the accounts and the migrations. The history and Grafana move into Compose on top of the same cupboards without losing data, proven by a history fingerprint that stays exactly the same, and Grafana now starts complete from files (provisioning). The services come back to life by themselves thanks to health checks and restart policies. On the Pi, the gateway broker moves into a container through `edge/compose.edge.yml` and forwards the data to the laptop through a LAN bridge, without new firmware; without a Pi, the simulator and the mock Garden take its place. You also back up the cupboards and test restoring them, drop the molds off at the GHCR image shop, then run the "clean laptop" test: from `git clone` to the **Login** page in < 10 minutes, with the history still there after `docker compose down` and then `up -d`. Everything is still on the home network, and a sleeping laptop puts the bot, the alerts, and the morning report to sleep with it; the internet, HTTPS, and TLS follow in Module 27.

Module 27 takes that home **to the internet**. The same center (`compose.cloud.yml`, now one file for the laptop, the VPS, and the Pi; only `.env` differs) moves to a 2 GB VPS with its doors locked: SSH keys, ufw, and Docker counters that are `127.0.0.1` only except 80, 443, and 8883, because Docker's counters go past ufw. A `.my.id` domain gives the names `iot.` and `mqtt.` (DNS only), and Caddy sets up automatic HTTPS from Let's Encrypt at `https://iot.yourname.my.id`, including Grafana at `/grafana/`. Backend 1.4.0 trusts Caddy through `TRUST_PROXY` (a `Secure` cookie, the `429` limit per visitor), uses a persistent broker session, and doesn't send a manual command again if it wasn't carried out within 2 minutes. Caddy's certificate is copied to Mosquitto (the one-off service `mqtt-certificate` and a weekly cron), so door 8883 only accepts TLS. The Pi → VPS bridge moves up to TLS and learns **store-and-forward**: when the home internet is unplugged for 10 minutes, the Pi holds the readings and then forwards them with their original `ts`, with no gaps and no duplicates, while commands aren't held, so that no stale command is carried out later. Dashboard 1.3.0 becomes an app on your phone (PWA) that a friend in another city opens over HTTPS. The free path runs everything on the Pi through Cloudflare Tunnel, with the broker staying on the home network. The data contract goes up to 1.5 (the message shapes stay), and the firmware doesn't change. The author tested it in a simulated internet on one Raspberry Pi, with stand-ins for Let's Encrypt and the phone; a real VPS, domain, and phone weren't tested yet when the module was published. The limit: the Node 1 firmware is still uploaded over a cable, and OTA follows in Module 28.

Module 28 makes that home **updatable**. The Node 1 firmware goes up to 1.7.0, the first version that can be updated over the air (OTA): it goes in over a cable for the last time, then the admin presses **Update** on the **Fleet** screen (`/fleet`, dashboard 1.4.0), the server gives the order over MQTT, and Node 1 pulls the 1.7.1 firmware file by itself from a locked route of backend 1.5.0 behind Caddy (`/fw/*`, the device key, a SHA-256 fingerprint, HTTPS on the internet) into the other program shelf. New firmware must prove itself within 60 seconds (connect to the broker, subscribe to `cmd`, and publish `online`); with the test release 1.7.2, whose key is broken on purpose, Node 1 goes back to 1.7.1 by itself (rollback). An update goes to one canary device first, and only then to the rest with **Update all**, which stays locked until the canary succeeds. A new board is registered in ±1 minute through the Wi-Fi portal and a single-use claim code, with a broker account the backend makes by itself through dynamic security (at the central broker, and at the Pi gateway through the bridge); **Deactivate** disconnects a lost device at once; `vitals` carries `reset_reason` and the version, and its interval is set from afar. The backend uses migration 011, the data contract goes up to 1.6, and `PIN-MAP.md` to version 7 with the pins unchanged: Node 1 moves from the breadboard into a project box with a screw-terminal expansion board, labels, and the Module 9 power supply, without 220 V, and then runs for 24 hours without a `BROWNOUT`. Node 2 stays 1.0.0 and is still updated over a cable. The author compiled firmware 1.7.0 with `arduino-cli` but hasn't run it on a board yet: the update, the rollback, and the claim were tested with simulated devices on one Raspberry Pi, and the box was written from dated sources, reconstructed diagrams, and licensed photos. The limit: server images that update automatically and automatic tests follow in Module 29, service monitoring and automatic backups in Module 30.
