# Sources & Image Credits — Module 26

A recap of all the images in this folder. The original curriculum diagrams are licensed **CC BY 4.0**, and their `.svg` files are included so they can be edited. The diagrams follow the code of this module (`compose.cloud.yml`, `.env.example`, `.gitignore`, `.gitattributes`, `scripts/fingerprint.sql`, `edge/compose.edge.yml`, `edge/center.conf`, `edge/gateway.conf`, `edge/bridge.example.conf`; backend 1.3: `Dockerfile`, `.dockerignore`, `package.json`; frontend 1.2: `Dockerfile`, `caddy/Caddyfile`, `src/socket.ts`; the `grafana/` folder: `provisioning/*`, `dashboards/system-health.json`, `grafana-user.sql`, `README.md`) and the behavior the author tested on a **Raspberry Pi 5 running Ubuntu 26.04 (arm64) playing both the laptop and the Pi**, like the Indonesian edition: Docker Engine 29.1.3 with Docker Compose 2.40.3 (the Ubuntu package, not Docker Desktop; the `docker compose` command is the same in Docker Desktop), TimescaleDB 2.30.2, Grafana 13.2.4, Mosquitto 2.1.2, Caddy 2.11.7, Node.js 24.22.1, Google Chrome 156. The Pi gateway ran as a second Compose project on the same machine with other counters, not on a real Raspberry Pi OS, and its device was the simulator `f00d00000001`, not a real ESP32; Telegram = a **mock Bot API server** in the author's lab, and the GitHub Container Registry (GHCR) was played by a **local registry** `registry:3.1.2` on `127.0.0.1`, so the GHCR login, the package page, and pulling an image from public GHCR were **not recorded**. The numbers in the diagrams are the author's lab numbers on a Pi 5 (arm64) with the module's final code (final test, 28 Oct 2026), the same story numbers as the Indonesian edition: image sizes (`docker image ls`: on disk / compressed download), build times, the `docker compose push` time, the clean-laptop test, and the `docker compose up -d` timeline (seconds on Compose's screen; your laptop may be faster or slower, and build times change with the network and the npm cache). The English lab of 29 Oct 2026 measured the same order of size and time (for example the web image 90.3 MB instead of 90.4 MB, `push` 4.0 s instead of 3.7 s). The full `npm ci` comparison (with the developer tools) (404 MB / 94.8 MB) comes from the author's research test on the base `node:24.21.0-alpine`. The restart policy's behavior on a *reboot* or a Docker restart is written from Docker's docs and code, **not tested** by the author; `docker compose up -d --build` on an amd64 laptop was not tested either. Windows/macOS-only parts (Docker Desktop, WSL 2, PowerShell) were not tested by the author. The laptop IP `192.168.1.10` and the Pi IP `192.168.1.37` are **examples**, the same as in the earlier modules.

The screenshots come from the author's English lab of 29 October 2026, on the same **Raspberry Pi 5 with Ubuntu 26.04 (arm64) playing the laptop**, with **headless Google Chrome 156 (`Chrome/156.0.8078.47`)** driven over the DevTools protocol: `--lang=en-US`, the time zone emulated as `Asia/Jakarta` (WIB), scale 2, width 1280 px (long pages with a temporarily taller window, still 1280 px wide; the 375 px width = **DevTools device mode on the same machine, not a real phone**), a fresh browser profile per scenario. They were taken against the whole home run by **Docker Compose 2.40.3** (Docker Engine 29.1.3, the Ubuntu package, not Docker Desktop) from this module's `compose.cloud.yml` as it is, plus one lab-only Compose file for the mock Telegram (not in the reader's project): TimescaleDB 2.30.2, Mosquitto 2.1.2, this module's real backend 1.3.0 and web 1.2.0 (Caddy 2.11.7), Grafana OSS 13.2.4 (`/api/health`: version 13.2.4, commit `0e79aef9d9`) in its **default dark theme** with provisioning from this module's `grafana/` folder, and Uptime Kuma 2.5.8. The "Module 25" Grafana cupboard was made in the English lab the way Module 25 made it (the old `docker run` containers, then the move of Practices 4–7); the Practice 7.3 takeover was done there through the same API requests the Grafana screens send, so the screens of the takeover itself are not in these pictures, only the result after `docker compose up -d`. The data senders are mock programs: the simulator `f00d00000001` and the **mock Garden** `f00d000000b2` (`tools/` of this module, every 300 seconds, never shortened) plus the practice history from `npm run seed-history`, not a real Node 1/Node 2; Telegram = a **mock Bot API server** in the author's lab (a fake bot token, the fake `chat_id` `777000222`, shown as it is), so there is no screenshot of the Telegram app and no picture shows the token. `grafana-provisioning-wrong` comes from a **separate test project with empty cupboards** (removed afterwards); the Uptime Kuma wizard ran on a fresh Uptime Kuma cupboard (removed afterwards) with a lab test account; the phone-mode shot used the lab machine's real LAN address for that one test, **sanitized to `192.168.1.10`**. There is no screenshot of Docker Desktop or the GitHub Container Registry (neither was tested by the author). No password, cookie, key, token, machine path, or real IP address appears in any picture, and no lab port or lab container name either (headless Chrome has no address bar). The sensor numbers and times are examples; times are written in WIB. Docker Desktop, Windows/macOS, the real GHCR, the real Telegram app, a real phone, a real ESP32, and a reboot were **not** tested by the author. The pass requirement in `roadmap-module-26` is quoted from the [Syllabus §7, Module 26](../../../SYLLABUS.md#module-26--docker--docker-compose-one-command-for-all-services).
