# Mini Smart Home Frontend

🌐 **English** · [Bahasa Indonesia](../../../proyek-rumah-pintar-mini/frontend/README.md)

Dashboard v2.0 of the Mini Smart Home project: a React 19 + TypeScript web page with Tailwind CSS v4, made with Vite 8 (the `react-ts` template from create-vite 9.3.1). Every screen has its own address (React Router v8, declarative mode), and the screens behind the login are guarded by protected routes. The dashboard shows live data from the backend through Socket.IO (the device list, details with a 5-minute chart and gauges, a 1 hour / 24 hours / 7 days history with its rows and a CSV), and since Module 24 it also **controls** the devices: an admin account turns the lamp and fan on with the status "Waiting for device confirmation…", waters with the pump, and creates, changes, deactivates, and deletes automation rules in a form checked by the same Zod schema as the backend. A viewer account sees all the data without control buttons. Important events (a rule acting, a device disconnecting) appear as toasts. Since Module 25 (v1.1) there is a **Map** screen: every device that has a point (`lat`, `lng` from backend 1.2) shows as a green/gray circle on an OpenStreetMap map, colored by its live status. It's designed to be tidy on a phone and on a laptop, follows the system's dark mode, and can be opened from a phone on the home Wi-Fi (see "Limits of v2.0"). With v1.1, the Phase 4 dashboard is complete: live data (Module 23), control and roles (Module 24), and the device map (Module 25, 🎉 Phase 4 checkpoint). The Grafana technical dashboard is NOT part of this folder: it runs separately in Docker, with its files in the project's `grafana/` folder.

**v1.2 (Module 26)** packs the dashboard as a **Docker image** (the `web` service in `compose.cloud.yml`, the project root): Node.js is only used while building, then **Caddy** serves what is in `dist/` at `http://localhost` and forwards every `/api/…` address to the backend, so the page and the API live at one address. The dashboard code only changes three lines in `src/socket.ts` (the live connection through the path `/api/socket.io/`), and `npm run dev` keeps working as before. Details in [How to run it with Docker Compose](#how-to-run-it-with-docker-compose-module-26) and [Version 1.2 notes](#version-12-notes).

**v1.3 (Module 27)** makes the dashboard an **app you can install** (a PWA, *Progressive Web App*) on phones and laptops: one new developer package, `vite-plugin-pwa` 2.0.0, writes a manifest (the app's name, icons, colors) and a service worker (a small helper in the browser that keeps the dashboard's shell) at `npm run build`. The tab icon is now a house (not the Vite logo anymore), and there are 192 and 512 px app icons. The home's data is never stored: the numbers are always requested from the server, and when the internet is down the installed app still opens with the message "Can't reach the server. Check your internet connection, then try again." Installing it needs a secure address, `https://` (a VPS or the Module 27 free path) or `http://localhost`. Details in [A phone app (PWA, Module 27)](#a-phone-app-pwa-module-27) and [Version 1.3 notes](#version-13-notes).

**v1.4 (Module 28)** adds the **Fleet** screen (`/fleet`, the **Fleet** menu): every device with its firmware version, its health from the last vitals (the restart reason, Wi-Fi signal, RAM, uptime), and its last update, plus the list of firmware releases on the server. An admin account uploads a `.bin` firmware file from the browser (the server computes its size and SHA-256), updates the firmware over the air (OTA) for one device, the canary devices, then all of them, creates single-use **claim codes** for new devices, sets the vitals interval, and **deactivates** a lost device. An update's progress (accepted → downloading → succeeded, rollback, or failed) shows by itself through Socket.IO, without polling. The `offline-mode` status is now written **stopped on purpose** on every screen. No new npm package; its partners are backend 1.5 and data contract 1.6. Details in [The Fleet screen (Module 28)](#the-fleet-screen-module-28) and [Version 1.4 notes](#version-14-notes).

**v2.0 (Module 29)** adds no screen. There are three new things. First, **one version number for the whole project**: the dashboard and the backend both jump to **2.0.0**, the number that is also the image tag, the Git tag `v2.0.0`, and the top entry of `CHANGELOG.md` in the project root. Second, that number **shows on the screen**: `v2.0.0` under the title of the **Login** screen and under the title of the dashboard header, read from `package.json` at build time. Third, **the dashboard's first automatic tests**: Vitest 5.0.5 with five tests of pure functions (WIB time, CSV, rule sentences), run with `npm test`. The GitHub Actions robot runs `npm run lint`, `npm test`, `npm run check-schema`, `npm run build`, and `npm audit` on every pull request, then builds the web image for two kinds of processor (amd64 and arm64) and pushes it to the GHCR image shop; the VPS and the Pi pull that image instead of building it themselves. The MAJOR number goes up (1.x → 2.x) because the way the project is deployed changed, not because the dashboard changed. Details in [Automatic tests (Module 29)](#automatic-tests-module-29), [The version number (Module 29)](#the-version-number-module-29), and [Version 2.0 notes](#version-20-notes).

## How to run it with Docker Compose (Module 26)

The everyday way ("home mode"): the dashboard starts together with the whole home, without Node.js and without `npm install` on the laptop. Every command is typed from the **project root** (the folder that holds `compose.cloud.yml`). The full steps are in [Module 26](../../phase-5-operations-scale/module-26-docker-compose/README.md).

1. Start the whole home as in the "How to run it with Docker Compose" section of `backend/README.md` (the root `.env`, then `docker compose up -d`). The `web` service only starts after the backend is `(healthy)`.
2. Open **`http://localhost`** in Chrome or Edge (no port number: counter 80). If port 80 on your laptop is already used by another program, change `PORT_WEB` in the root `.env` (for example `8081`), write the same address in `CORS_ORIGIN` in that `.env` (`http://localhost:8081,http://127.0.0.1:8081`), run `docker compose up -d` again, then open `http://localhost:8081`. Without a matching `CORS_ORIGIN`, the **Log in** button is answered with `403 request from the page http://localhost:8081 refused`.
3. Log in with your account. The Module 20 accounts are in the database cupboard, so they stay valid; on a new laptop, make the first account with `docker compose exec backend …` (see `backend/README.md`).

| Command (from the project root) | What it does |
| :--- | :--- |
| `docker compose ps` | `web` must be `Up`. The PORTS column also writes `443/tcp, 2019/tcp, 443/udp`: that's only a note the Caddy image ships with; the only port really opened to the laptop is `127.0.0.1:80->80/tcp` |
| `docker compose logs web` | the Caddy log (JSON format). Four `"level":"warn"` lines at startup are normal in Module 26: `admin endpoint disabled`, `server is listening only on the HTTP port, so no automatic HTTPS will be applied to this server`, `HTTP/2 skipped because it requires TLS`, and `HTTP/3 skipped because it requires TLS`. They are also normal on the laptop since Module 27 (`WEB_DOMAIN` empty = HTTP only); on the VPS, Caddy writes its own certificate log (see Module 27) |
| `docker compose build web` then `docker compose up -d web` | **on the laptop**: rebuilds the image yourself after the dashboard code changed (tag = `version` in `package.json`). Since Module 29, the VPS and the Pi don't build: they pull the robot's image from GHCR (`scripts/deploy.sh`, see the project root README). On the author's Raspberry Pi 5, v1.4: 35.9 seconds (`npm ci` 16.8 seconds + `npm run build` 17.4 seconds) after `package.json` changed, ±20 seconds when the library list doesn't change (only `npm run build` is repeated). v1.3 was recorded at ±127 seconds (`npm ci` ±67 seconds): how long `npm ci` takes depends mostly on the package download speed at that moment, not on the dashboard code |
| `docker compose restart web` | reads `caddy/Caddyfile` again after you changed it (±1 second) |

**How it works.**

- **Two stages** ([`Dockerfile`](Dockerfile)). The `build` stage (`node:24.22.1-alpine3.24`) runs `npm ci`, then `npm run build`. The final stage (`caddy:2.11.7-alpine`) only carries what is in `dist/` (at `/srv`) and the `Caddyfile`: no Node.js, no `node_modules`, no source code. Since v2.0 the `build` stage is written `FROM --platform=$BUILDPLATFORM …`: it always runs on the processor of the building machine, also when the robot builds the arm64 image on an amd64 machine, because the content of `dist/` is the same for every processor; only the final stage (Caddy) is taken for the target processor (Module 29). The author's image (Raspberry Pi 5, arm64) is **90.5 MB** on disk and **24 MB** compressed (what is downloaded from the image shop) for v1.4 (v1.3: 90.4 MB). The [`.dockerignore`](.dockerignore) keeps out your laptop's `node_modules`, `dist`, and `.env.local`, and since v2.0 also the test files `src/**/*.test.ts`.
- **The API address is built in at build time.** The line `ARG VITE_API_BASE=/api` in the `Dockerfile` (filled in by `args` in `compose.cloud.yml`) makes Vite write the text `/api` straight into the JavaScript, replacing the default address "the page's host name + `:8080`". Changing it means rebuilding the image; the image never reads `.env.local`.
- **One address for the page and the API.** Caddy ([`caddy/Caddyfile`](caddy/Caddyfile)) forwards every address that starts with `/api` to the backend and drops the prefix: `http://localhost/api/devices` → `backend:8080/devices`. `backend` is the service's name in the Compose hallway. Because the page and the API are both `http://localhost`, the browser needs no cross-port CORS permission, and the `SameSite=Strict` cookies are sent along.
- **The live connection.** Socket.IO reads `io("/api")` as a *namespace* (a room's name inside the server), not a path, so the badge never becomes **Live** (`connect_error: server error`). That's why `src/socket.ts` changed in v1.2: if `BASE` starts with `/` (or is empty), the path is given through the `path` option (`/api/socket.io`). In dev mode `BASE` holds a full address (`http://localhost:8080`), so the old way is still used.
- **The path of the `session` cookie.** The backend sets the `session` cookie (the 7-day season pass) with the path `/auth`, while from the browser its address is `/api/auth`. The line `header_down Set-Cookie "Path=/auth" "Path=/api/auth"` in the Caddyfile changes its path; without it you're thrown back to the **Log in** screen every 15 minutes (the refresh is answered with `401 not logged in: no session cookie`). The backend itself doesn't change.
- **Every screen address is answered with `index.html`** (*SPA fallback*, Module 24's promise): `try_files {path} /index.html`. F5 on `/map` or `/devices/f00d00000001` still opens its screen. The JavaScript and CSS files under `/assets/…` don't follow that rule: a file that doesn't exist (for example `/assets/old.js`) is answered with `404`, not the `index.html` page.
- **A new dashboard is used quickly.** The `index.html` page is sent with `Cache-Control: no-cache`: the browser always asks Caddy first before using its saved copy (Caddy answers `304` when nothing changed). Since v1.3 the same rule applies to `sw.js` and `manifest.webmanifest`, so the browser learns quickly that there is a new version; but because the service worker serves the shell from its store, a new version only shows on the **next opening**, after the browser has finished fetching it in the background (see "A phone app"). The `/assets/…` files may be kept long by the browser, because their names carry a fingerprint and change with every build.
- **The Caddyfile from the repo.** Compose mounts the `frontend/caddy/` folder at `/etc/caddy` (read-only); the copy inside the image is only used when the image runs on its own. Caddy only reads that file when it starts (`admin off`), so after changing it: `docker compose restart web`.
- **HTTP on the laptop, HTTPS on the internet (Module 27).** The site address in the Caddyfile is `{$WEB_DOMAIN::80}`: when `WEB_DOMAIN` in the root `.env` is empty (laptop, free-path Pi), Caddy serves plain HTTP on port 80 for any name typed, exactly as in Module 26. On the VPS, `WEB_DOMAIN=iot.yourname.my.id`: Caddy asks Let's Encrypt for a certificate by itself, serves HTTPS, and redirects `http://` to `https://`. The broker's address (`MQTT_DOMAIN`) is answered with `404` "This address is for the MQTT broker (port 8883), not the dashboard.", and `/grafana/` is forwarded to Grafana when `GRAFANA_URL` is filled in (see `grafana/README.md`). The steps are in [Module 27](../../phase-5-operations-scale/module-27-deploy-internet-tls-pwa/README.md).
- **Backend down?** The page still opens (Caddy serves it), but every `/api` request is answered with an empty `502`: the **Log in** screen writes `Something went wrong (502).`, and a dashboard that is already open shows the **Reconnecting…** badge until the backend is back. `docker compose logs web` writes the reason, for example `dial tcp: lookup backend on 127.0.0.11:53: server misbehaving` (the `backend` service was stopped) or `connect: connection refused` (the backend is starting). Check `docker compose ps` and `docker compose logs backend`.
- **Firmware downloads `/fw/…` (Module 28)** are forwarded by Caddy to the backend as they are: no compression, no prefix removed (the `handle /fw/*` block in the Caddyfile, the infrastructure part). This address is for devices, not browsers: the backend checks the device key, so opening it in a browser is answered `403` `{"message":"needs Basic Auth device_id:key"}`, also after the service worker is active (tried by the author). Caddy never serves firmware files directly: the `firmware-data` cupboard is only mounted in the backend.
- **The device door `:8081` (Module 28, the free-path Pi).** The Caddyfile has a second site on door 8081 that only forwards `/fw/…` and `/api/provision/claim`; anything else is answered `404`. On the free-path Pi, the root `.env` writes `WEB_ADDRESS=<Pi IP>` + `WEB_INNER_PORT=8081`, so the home Wi-Fi only sees that door, while the dashboard still goes through the tunnel (cloudflared knocks on `http://web:80`). The trust in `X-Forwarded-For` (`CADDY_TRUSTED_PROXIES`) only applies on door 80 (`servers :80` in the Caddyfile): if it applied to the home Wi-Fi too, any phone there could fake its address and get past the login and claim rate limits. On the laptop and the VPS, door 8081 isn't connected to the outside.
- **The API docs** stay at the backend counter, `http://localhost:8080/docs` (see `backend/README.md`). `http://localhost/api/docs` can't be used behind Caddy: its page assets have the wrong address, and the **Try it out** button calls the API without the `/api` prefix.

**Trying this image on its own** (without Compose, from the `frontend` folder, without the `backend` folder): `docker build -t mini-smart-home-web:2.0.0 .`, then `docker run -d --rm --name try-web -p 127.0.0.1:8088:80 mini-smart-home-web:2.0.0`. `http://localhost:8088/` and `http://localhost:8088/map` answer with the dashboard page (200), while `http://localhost:8088/api/health` answers `502`, because outside Compose there is no service named `backend`. Stop it with `docker stop try-web`.

## Dev mode (Vite, `npm run dev`)

To change the dashboard code: Vite updates the page every time a file is saved (HMR), without building an image. In this mode the dashboard calls the **dev-mode** backend (`npm run dev` in the `backend` folder; see the "Dev mode" section of `backend/README.md`), because the `CORS_ORIGIN` of the Compose backend only allows `http://localhost`. Only one backend may run: from the project root, `docker compose stop backend web` first; done developing, **Ctrl + C** in both `npm run dev` terminals, then `docker compose start backend web`.

1. Install Node.js 24 LTS (Vite 8 needs at least Node.js 20.19 or 22.12; React Router 8 needs Node.js 22.22 or newer).
2. Start the dev-mode **backend** as in `backend/README.md` (the `db` database and the central `mosquitto` broker from Compose keep running, then `npm run dev` in the `backend` folder; before Module 26: the `smarthome-db` database in Docker Desktop and the MQTT broker) together with its data sources: Node 1 and Node 2 (Kit A + B), or the device simulator in the `tools` folder with the practice device `f00d00000001` already registered. The **Map** screen needs backend 1.2 or newer (backend 1.1 doesn't send `lat`/`lng`; the Map screen then writes "The backend doesn't send map points (lat, lng) yet. The Map page needs backend 1.2 (Module 25)."), and at least backend 1.1 for the other screens: "falls below" rules (for example water if soil < 30%) and the **Delete rule** button don't exist in backend v1.0. `CORS_ORIGIN` in `backend/.env` must contain `http://localhost:5173` (its default value already does).
3. In this folder, run `npm install`.
4. Run `npm run dev`, then open **`http://localhost:5173`** in Chrome or Edge. Use `localhost`, not `127.0.0.1`: on Windows, Vite only listens on `localhost`, and the page's host name must be the same as the API's host name so the login cookies are sent along.
5. Log in with an account made in Module 20: `admin@home.test` (looks and controls) or `viewer@home.test` (can only look). The password is your own; the dashboard never stores it.

The 7-day history needs 7 days of data. If the "7 days" chart only has a few points, fill in practice data in the `backend` folder with `npm run seed-history`, then refresh the hourly summary book (from the project root; before Module 26 the command was `docker exec smarthome-db psql …`):

```
docker compose exec db psql -U postgres -d smarthome -c "CALL refresh_continuous_aggregate('readings_hourly', now() - INTERVAL '8 days', now() - INTERVAL '1 hour');"
```

| Command | What it does |
| :--- | :--- |
| `npm run dev` | a dev server at `http://localhost:5173` that updates the page every time the code is saved (HMR). Its port is locked (`strictPort`): if 5173 is in use, Vite stops with an error instead of quietly moving to 5174 |
| `npm run dev:phone` | the same as `npm run dev`, but other devices on the home Wi-Fi can open it too (`vite --host`). Only for "phone mode", see below |
| `npm run build` | checks the TypeScript types (`tsc -b`), then makes a ready-to-use version in the `dist/` folder. One yellow warning `Some chunks are larger than 500 kB after minification` is normal since Module 23 (the Recharts chart library makes its JavaScript file big; since Module 25, Leaflet adds about 157 kB, or 46 kB after gzip compression); the build still succeeds. Since v1.3 its output ends with the section `PWA v2.0.0`, `mode generateSW`, `precache 10 entries (…KiB)`, and `files generated` `dist/sw.js` + `dist/workbox-….js` |
| `npm run preview` | serves what is in `dist/` at `http://localhost:5173` so you can try it (stop `npm run dev` first). For a phone: `npm run preview -- --host`. Not a real server: since Module 26, `dist/` is served by Caddy in the web image. **Since v1.3:** preview installs a service worker at `http://localhost:5173`, and a later `npm run dev` at the same address keeps showing the OLD build result from its store. Before going back to `npm run dev`, open DevTools → **Application** → **Storage** → **Clear site data** (see "A phone app") |

The packages added in Module 24 are installed with written versions: `npm install react-router@8.5.0 react-hook-form@7.91.0 @hookform/resolvers@5.9.2 zod@4.6.7`. The command without versions can fail (`npm error code ERESOLVE`, because of `@hookform/resolvers` 6.0.0); don't use `--legacy-peer-deps`.

The PWA package (Module 27) is a **developer** package (`-D`, only used while building) with an exact version: `npm install -D -E vite-plugin-pwa@2.0.0`. It pulls in about 300 helper packages (Workbox, Babel), so `node_modules` grows from ±245 MB to ±321 MB; what is in `dist/` only grows by ±16 kB. The audit summary npm writes after installing (also after `npm ci`) depends on the date. As of 2 November 2026, with the 1.4.0 `package-lock.json`, npm writes `10 vulnerabilities (2 low, 8 moderate)` (in Module 27: `4 low severity vulnerabilities`; since then two new vulnerability reports were published, for `glob` and `minimatch`). All of them are in build tools installed as developer packages: the old `deepmerge` Workbox uses, and `glob` and `minimatch` through `workbox-build` under `vite-plugin-pwa`. Those tools only run on your laptop at `npm run build` and don't go to the browser: `npm audit --omit=dev` (the packages that go to the browser) writes `found 0 vulnerabilities`. **Don't** run `npm audit fix --force`: as of the same date its suggestion goes *down* to `vite-plugin-pwa` 1.1.0, an old version, not a fix.

The map packages (Module 25) are installed with written versions too: `npm install leaflet@1.9.4 react-leaflet@5.0.0`, then `npm install -D @types/leaflet@1.9.22`. Don't copy the command from react-leaflet's installation page (`react@rc`, `react-leaflet@next`): as of October 2026 it installs old test versions (React 19.0.0-rc.1, react-leaflet 5.0.0-rc.2).

## Automatic tests (Module 29)

Since v2.0 the dashboard has automatic tests of its own, written with **Vitest 5.0.5**, the same tool as the backend (Module 19). Its version is written exactly in `package.json` (`"vitest": "5.0.5"`, without `^`), so the laptop and the robot use the same Vitest. What is tested so far are **pure functions**: an input goes in, an output comes out, no screen, no backend, no network.

The four checks below are also run by the GitHub Actions robot on every pull request (the job `verify`, Module 29). Type them from the `frontend` folder, after `npm install`:

| Command | What it does | The right result |
| :--- | :--- | :--- |
| `npm run lint` | oxlint 1.89.0 looks for common mistakes in the code, the test files too; even a warning makes the robot red (`--deny-warnings`) | `Found 0 warnings and 0 errors.` |
| `npm test` | Vitest once (`vitest run`): five tests | `Test Files  3 passed (3)` and `Tests  5 passed (5)`, exit code 0 |
| `npm run check-schema` | the schema copies in `src/schemas/` are the same as the backend's | two `SAME` lines |
| `npm run build` | TypeScript (`tsc -b`, which also checks the test files), then Vite | `✓ built in …`, exit code 0 |

Plus one library security check: `npm audit --omit=dev --audit-level=high`. `--omit=dev` = only the libraries that go to the browser; `--audit-level=high` = exit code 1 only for a `high` or `critical` hole. As of 4 November 2026 its result is `found 0 vulnerabilities` (exit code 0). `npm audit` without those two options writes `10 vulnerabilities (2 low, 8 moderate)` and exit code 1: all of them in developer tools (`deepmerge`, `glob`, and `minimatch` through `vite-plugin-pwa` and Workbox), which don't go to the browser. That number is the same as v1.4: Vitest doesn't add to it. Audit numbers change every time a new hole is announced, so check again on the day.

**Expected output** (`npm test` on the author's Raspberry Pi 5, Node.js 24.21.0):

```
> mini-smart-home-frontend@2.0.0 test
> vitest run


 RUN  v5.0.5 /home/…/mini-smart-home/frontend

 ✓ src/csv.test.ts (2 tests) 37ms
 ✓ src/rules.test.ts (1 test) 41ms
 ✓ src/time.test.ts (2 tests) 25ms

 Test Files  3 passed (3)
      Tests  5 passed (5)
   Start at  …
   Duration  3.86s (import 90%, transform 7%, tests 2%, worker 1%)
```

Vitest runs the three files at the same time, so the order of the `✓` lines can differ on your computer. `npx vitest run --reporter=verbose` writes the names of the five tests one by one.

The five tests sit next to the files they test:

| File | Function | What it guards |
| :--- | :--- | :--- |
| `src/time.test.ts` | `wibTime` | the time is always WIB, whatever the computer's time zone. The test tries it in UTC (the GitHub Actions robot's time zone), WIB, WITA, and WIT through `vi.stubEnv("TZ", …)`: `09:27:10` UTC = `16:27:10 WIB`, and `17:05` UTC = `00:05:00 WIB` |
| `src/time.test.ts` | `relativeTime` | `just now` under 5 seconds, also when the server clock is 2 seconds ahead of the phone clock (not `in 2 seconds`); after that `45 seconds ago`, `3 minutes ago` |
| `src/csv.test.ts` | `toCsv` | a CSV for Excel with English (US/UK) settings: a comma separator, a decimal point (`28.5`), a name holding a comma wrapped in double quotes, `null` as an empty cell, a BOM at the start of the file, CRLF at the end of every line |
| `src/csv.test.ts` | `csvTime` | a WIB time as `2026-10-24 16:15:42`, which still sorts right in Excel; the date changes too after WIB midnight |
| `src/rules.test.ts` | `describeRule` | the sentences on the **Rules** screen: the Module 19 fan rule (`… above 30 °C for 60 seconds, turn on the fan. The fan turns off again after the temperature falls below 28.5 °C.`) and the morning watering schedule (`Every day at 06:00 WIB, water for 5 seconds on Garden. Notify via Telegram.`) |

**When a test turns red.** For example `timeZone: "Asia/Jakarta"` is deleted from `wibTime` in `src/time.ts`. A laptop set to WIB still writes the right time, so this mistake slips through easily; the robot (UTC) and a phone in another zone don't. The `wibTime` test catches it on any computer:

```
 FAIL  src/time.test.ts > the clock on the screen (time.ts) > wibTime: WIB time, whatever the computer's time zone
AssertionError: expected '09:27:10 WIB' to be '16:27:10 WIB' // Object.is equality

Expected: "16:27:10 WIB"
Received: "09:27:10 WIB"
```

Below it Vitest points at the failing test line, then writes `Tests  1 failed | 4 passed (5)`. `npm test` ends with exit code 1, and the robot gives a red cross. The author tried it on a throw-away copy, together with seven other small mistakes (for example a semicolon separator in the CSV, `"sv-SE"` replaced by `"en-GB"` in `csvTime`, or the schedule time `6:00` without a leading zero): all of them were caught.

**Good to know.**

- **No `vitest.config.ts`.** Vitest reads the same `vite.config.ts` as `npm run dev` and `npm run build`. The React, Tailwind, and PWA plugins are loaded too but have no effect: the tests run in Node.js, without a browser (Vitest's default environment, `node`; no jsdom). Vitest looks for every `*.test.ts` file outside `node_modules`.
- **TypeScript checks the tests too.** `tsconfig.app.json` checks the whole of `src/`, so `npm run build` also checks the test files. That's why every test file writes `import { describe, expect, it } from "vitest"`: Vitest is used without globals. The Node.js types Vitest brings along don't leak into the dashboard code: `process` is still unknown in `src/` (tried by the author).
- **The tests aren't in the image.** `.dockerignore` holds back `src/**/*.test.ts`, so changing only a test doesn't change the content of the web image.
- **Tailwind only reads the dashboard code.** `src/index.css` limits the places where Tailwind looks for class names to the `src/` folder (without the test files) and `index.html`. Without that limit Tailwind reads every text file in the `frontend` folder, this README included: the word `transform` in the Vitest output example above once became a real CSS class, so changing only a document changed the CSS of the web image too (a finding of the Module 29 lab).
- **Why ±3–4 seconds for five small tests?** Almost all of it is the time to load the whole of `date-fns` (all its functions) for `time.test.ts`: see `import 90%` in the `Duration` line. Without that file, `csv.test.ts` and `rules.test.ts` finish in ±0.6 seconds. In the browser there is no difference, because Vite only takes the parts of `date-fns` that are used.
- **Time zones in the tests.** `vi.stubEnv("TZ", …)` only affects a format made WHEN it is called, such as `toLocaleTimeString` in `wibTime`. The `Intl.DateTimeFormat` formatters made once when the file loads (for example `HOUR_MINUTE` in `time.ts`) use the time zone at load time: a test for a `wibHourMinute` or `wibDateTime` that forgot `timeZone` stays green on a WIB laptop, and only turns red on the robot with its UTC clock.
- **Watch mode.** `npx vitest` (without `run`) waits, then runs the tests again every time a file is saved; press `q` to quit. On the robot, which has no terminal, Vitest always runs once.
- **Adding a test.** Make `src/<name>.test.ts` next to `src/<name>.ts`, for a file that is safe to load in Node.js. **Don't** import `src/api.ts` or a file that imports it (for example `src/fleet.ts`, `src/socket.ts`, and the screen components): `api.ts` reads the browser's `location` when it loads, and the test turns red with `ReferenceError: location is not defined` (tried by the author). With `VITE_API_BASE=/api npm test` that error goes away, but it's better to keep the tests on pure functions.
- **On the robot**, the job `verify` runs the same commands in a `node:24.22.1-alpine3.24` container (the same Node.js as the image's build stage), starting with `npm ci`, not `npm install`: `npm ci` installs exactly the content of `package-lock.json` and fails when `package.json` and the lock don't match.

## The device map (Module 25)

- **The source of the points** is the `lat` (latitude) and `lng` (longitude) columns of `devices` in the database, which backend 1.2 sends in `GET /devices`. Points are set by an **admin** through the API, not written in the frontend code: the Bruno request `set device location` (`PUT /devices/:id/location` with `{ "lat": -6.1754, "lng": 106.8272 }`; numbers with a decimal point, `null` + `null` removes the point). A viewer account is answered 403.
- **When does a new point show up?** The Map screen fetches `GET /devices` again every time it opens. A point changed through Bruno shows after you open the **Map** menu again (from another screen), without F5. While the Map screen is open, points don't move by themselves: point changes aren't sent through Socket.IO. If that fetch fails (for example the database is down for a moment), the map keeps using the list it already has and a toast says "Couldn't reload the device list: the map points may not be the latest."; the other screens aren't affected.
- **The color** follows the live status in the store (Socket.IO events, no polling): green = `online`; gray = offline, offline mode, unknown, or a key that is revoked / not registered (its messages are ignored by the backend). A color always comes with words: the legend under the map and the status badge in the popup. Remember, "online" is the last MQTT status: a silent Node 2 (the Garden) stays green until its `offline` status is published (16 minutes after its last packet), and stays green while its linking Node 1 is off too (Node 2's status is published by Node 1). So "last seen" in the popup still needs reading, and for "data stopped arriving" rely on the "silent node" alert in Grafana.
- **The popup** (tap a circle): name, location, `device_id`, status, "last seen", and the link **Open details →** to `/devices/<id>`.
- The map is **fitted** to all points (`fitBounds`, zoom 18 at the closest) when it opens and when a point moves, not when a status changes, so a map you are dragging doesn't jump by itself. Devices without a point are listed under the map ("No point yet: …"). If there is no point at all yet, the screen says "No device has coordinates yet. Set them with the Bruno request `set device location`."
- **Marker = `CircleMarker`** (an SVG circle), not Leaflet's default `Marker` with an icon: the default icon uses image files that go missing after `npm run build` (the markers vanish in `npm run preview`, although they show in `npm run dev`). A circle needs no image file.
- **The map box must have a height** (`h-96` = 384 px in `DeviceMap.tsx`; without a height, the map is 0 px tall and can't be seen), and Leaflet's CSS must be loaded (`import "leaflet/dist/leaflet.css"`; without it the tiles are scattered). The `isolate` class keeps Leaflet's layers (z-index 400–1000) inside the map box, so the toasts (z-50) still show above it.
- **Map tiles** come straight from the OpenStreetMap server (`https://tile.openstreetmap.org/{z}/{x}/{y}.png`, one constant in `src/map.ts`, as the OSM tile policy says: "don't hard-code the tile URL in many places"). The conditions: the attribution "© OpenStreetMap contributors" is always shown in the corner of the map (don't take it away), the browser sends a *Referer* (browsers do by default), and you **may not** download tiles in bulk or store them for use without the internet. This tile service is free without guarantees (no SLA) and can be blocked if overused; a few points for one home are far below that limit.
- **Dark mode:** the page frame, the legend, and the popup box with its ✕ button turn dark too (the rules in `index.css`); **the map tiles stay light**, because they are pictures from OpenStreetMap whose colors we don't change.
- **Privacy:** a home's coordinates are personal data (your home address). The examples in the module use a fictional point in a public place (around Monas, Jakarta). Before sharing a screenshot of the map, use the example point or cover the place.
- **Map library licenses:** Leaflet 1.9.4 is under the BSD-2-Clause license. react-leaflet 5.0.0 (with `@react-leaflet/core`) is under the **Hippocratic License 2.1**: free to use and change, provided the use is in line with human-rights principles (the UN Universal Declaration of Human Rights, named in its license text). That extra condition makes it **not** an open-source license recognized by the OSI (GitHub shows it as `NOASSERTION`). For this learning project that isn't a problem; for a product you sell, read its full text first (`node_modules/react-leaflet/LICENSE.md`), or use Leaflet directly without react-leaflet (covered in the Module 25 Deep Dive).

## The Fleet screen (Module 28)

The `/fleet` screen (the **Fleet** menu) is the firmware control room of every device. Its data comes from backend 1.5 (`GET /fleet` and `GET /firmware`); every role may look, its buttons are only drawn for admins. The full steps are in [Module 28](../../phase-5-operations-scale/module-28-ota-provisioning-fleet/README.md).

- **A device card** (`components/FleetCard.tsx`): name, kind, location, `device_id`, "last seen", the status badge (**Online**, **Offline**, **stopped on purpose**, or **deactivated**), **canary**, and **needs update** (a Node 1 whose version is older than the latest release). Under it: the firmware version, the health from the last vitals (the restart reason `reset_reason` with its meaning, the Wi-Fi signal with the categories of the Module 10 RSSI table, free RAM, uptime, the vitals interval), and the last update (status, version from → to, time, reason). **Update history** (at most 20, newest on top) is only fetched from the server when it is opened. One card shape for phones and laptops (two columns on a phone, three from 640 px), not a table: the dashboard's content column is only 768 px.
- **The restart reason** is colored by its meaning: `BROWNOUT` yellow (the voltage dipped: check the power supply), `PANIC` and `WDT` red (the program crashed or got stuck), `SW` blue (restarted by the program: an update, a rollback, `restart`), `POWERON`, `DEEPSLEEP`, and `UNKNOWN` gray. Firmware before 1.7.0 doesn't report it: "— (the old firmware doesn't report it)".
- **stopped on purpose** = the `offline-mode` status (contract 1.6): the device disconnects cleanly on purpose before it restarts (installing new firmware, or the Serial command `restart`). Its badge is sky blue, not red, and it is usually back **Online** within ±1 minute. Since v1.4 the same badge is used on the Devices and Details screens (it used to say "offline mode", which got mixed up with the offline mode of Module 19).
- **Node 2** shows with the version from its packet and the sentence "OTA isn't available for Node 2: update it by cable.", without an Update button.
- **Upload firmware** (admin, `components/FirmwareUpload.tsx`): a `.bin` file, a version `x.y.z` (the same as `FIRMWARE_VERSION` in that file), notes (at most 200 characters), and the **test** tick (a release broken on purpose for rollback practice: per device only, never "all", not counted as the latest release). Before sending, the browser refuses a file that doesn't end in `.bin`, a `*.merged.bin`, `*.bootloader.bin`, or `*.partitions.bin` file, an empty file, a file over 1,966,080 bytes (one program shelf), and a file whose first byte isn't `0xE9`, and also a version that isn't `x.y.z` (the same version rule as the contract: `OtaReport.shape.version` from the schema copy). The file's content is sent **as it is** (`fetch` with a `File` body and `Content-Type: application/octet-stream`, not a multipart form); the backend checks everything again and computes the SHA-256 itself. The result (the size and the `sha256`) shows under the form: compare it with `sha256sum` (Linux, macOS) or `Get-FileHash` (PowerShell). Errors from the backend, for example a version that already exists (`409`), are written in the form.
- **Firmware releases** (`components/ReleaseList.tsx`): newest on top, with the badges **latest**, **test**, or **withdrawn**, the size (and its percentage of one shelf), the `sha256`, the notes, the upload time, and the canary summary. An admin gets **Update canary** (every Node 1 marked canary) and **Update all**, which is locked ("Locked: no canary has succeeded yet.") until at least one canary has **succeeded** with that version and no canary failed; the server decides (`can_update_all`). The result (the devices that were sent the command and the skipped ones with their reasons) shows under that release. Devices that are offline or already updating are skipped, **not queued**: update them again later.
- **The buttons on a card** (admin, `components/FleetActions.tsx`): a version choice (the latest release by default, also after a new release is uploaded; a test release can be chosen) + **Update**; **Canary**; and under **More settings**: the vitals interval 60–3600 seconds (`telemetry` stays 10 seconds; Wi-Fi, the server address, and the key can't be changed from afar) and **Deactivate**. Update, Update canary, Update all, and Deactivate always ask first in an "are you sure?" box on the page (`components/ConfirmButton.tsx`, the **Delete rule** pattern of Module 24: the **Cancel** button gets the focus at once). The Update button is disabled, with its reason written out, if the device is deactivated, a Node 2, of a kind not known yet, `SERVER_URL` in the server's `.env` isn't set, there is no release yet, the previous update is still running, the device isn't online, or the chosen version is the one in use. The backend still checks again (409), for example a downgrade: tick **Allow downgrade** in the "are you sure?" box. A button's error (for example the `503` of Deactivate: "not saved in the database yet … repeat this step in a moment") stays on the card until **Close** is tapped (`components/ErrorBox.tsx`), it doesn't vanish like a toast.
- **A `202` answer = accepted, not finished.** The card then changes by itself through the Socket.IO `ota` event: **accepted by the device**, then **stopped on purpose** + **downloading**, then **Online** with **succeeded** (the new version), or **back to the old version (rollback)**, **failed** (with its reason, for example `SHA-256 doesn't match the command (Update 15 UPDATE_ERROR_SHA256)`), **rejected by the device**, or **expired (no word)**. A finished update makes the screen fetch `GET /fleet` and `GET /firmware` again (versions, health, the canary summary).
- **New devices** (admin, `components/CreateClaimCode.tsx`): **Create code** with a name and a location (optional) and a validity of 5–60 minutes (default 30). The code `XXXX-XXXX` is shown **once** in a read-only box with a **Copy** button (copying automatically only works at a secure address, `https://` or `localhost`; at `http://<IP>` the code is selected so you can copy it with Ctrl + C). The code isn't stored anywhere in the browser: it is gone when **Close** is tapped or the screen is left. Under it, "Recent codes (without the code)": still valid, already used (by which `device_id`), or expired. A device that registers with that code appears on the Fleet screen by itself (a `provisioning` event), then its kind and version fill in as soon as its first message arrives.
- **Deactivate** = `POST /devices/:id/revoke` (backend 1.5): the key is revoked, the broker account is deleted (the device is disconnected at once), and the server writes the `offline` status. The card becomes **deactivated**; the manual steps still needed (for example an old line in the Module 21 broker password file) show on the card until it is closed. The device only comes back with a new key or a new claim code.
- **Live without polling.** The status, the version (from `telemetry`), and an update's progress come through Socket.IO. Other data is only fetched again when there is news: an update finished, a `provisioning` or `revoked` event, the live connection back, or your own button (`fleetVersion` in `store.ts`, the `rulesVersion` pattern of the Rules screen). Health (vitals, every 5 minutes by default) isn't sent through Socket.IO: its numbers come from the last fetch, with the time of their vitals written beside them.

## Roles: admin and viewer

- The role is read from the `GET /auth/me` and `POST /auth/login` answers, then kept only in the tab's memory (the Zustand store), never in `localStorage`.
- The control buttons, **+ New rule**, **Edit**, and (since v1.4) the Fleet screen's buttons are only drawn once the admin role is **certain** (`useAdmin()` in `store.ts`), so they don't flash up on a viewer's screen.
- Leaving buttons out is only screen convenience, **not protection**. What guards is still the backend's guard: every command and change from a viewer account is answered `403 viewer accounts can only look; commands and changes are admin-only`, from the dashboard, Bruno, or any other way.
- A role changed with `npm run users` in the backend only shows after the page is reloaded or the access wristband (15 minutes) is renewed.

## Control buttons

- **Lamp and fan** (`components/SwitchButton.tsx`): as soon as it is tapped, the button changes at once (*optimistic UI*, React 19's `useOptimistic` + `useTransition`) and writes "Waiting for device confirmation…" until the backend passes on the device's answer (the ack, at most 5 seconds). Its final state is taken from the ack. If the command fails, the button goes back by itself to the state the device reports, and a toast explains why: the device refused (`ack.ok` `false`), 409 (the device is offline, the previous command is still waiting), 503, the server didn't answer. A **504** answer means "not confirmed by the device yet; the server tries again if it hears from the device within 2 minutes": a lamp or fan command isn't cancelled yet, so the lamp may turn on by itself a little later. Since backend 1.4 (Module 27), a command from the dashboard or Telegram that the device still doesn't carry out is forgotten after 2 minutes (the backend log: `… not carried out for more than 2 minutes: not sent again`), so that the lamp doesn't suddenly turn on hours later when the home internet comes back.
- **Pump** (`components/PumpButton.tsx`): 3, 5, or 10 seconds (the buttons say `3 sec`, `5 sec`, `10 sec`), deliberately **not** optimistic (water that has come out can't be pulled back; a repeated command = watering twice). The screen only changes after the ack, and its buttons stay disabled while the pump is still watering. The backend doesn't send a pump command again after a 504.
- The buttons are disabled (with the reason written) when the device isn't online or its kind isn't known yet. Node 2 and devices whose key is revoked or that aren't registered have no **Controls** section. The curtain is only shown (its button: the Module 24 Challenge).
- The `POST /devices/:id/command` answer is checked with the `Ack` schema (a copy from the backend) using `safeParse`, not just trusted.

## Automation rules

- The `/rules` screen writes every rule as a sentence (`describeRule()` in `src/rules.ts`), for example "If the soil moisture on Practice living room is below 30 % for 10 seconds, water for 5 seconds (once). The rule is ready again after the soil moisture rises above 35 %." This sentence is made in the browser, so it can differ a little from the event sentences the backend makes.
- There is one form for creating and changing (`components/RuleForm.tsx`, with three small parts `WhenSection.tsx`, `ThenSection.tsx`, and `ConfirmDelete.tsx` that use the same form through `FormProvider`): **When?** (a number rising above a limit, a number falling below a limit, or a set time with a 5-field WIB cron), **Then?** (turn the lamp/fan on while the rule is on, or send one command once), a sentence preview that changes while you type, the **Active** switch, and **Delete rule** with a confirmation. The input is checked by the `Rule` schema that is the same as the backend's (react-hook-form + `zodResolver`); Zod's built-in messages are replaced by friendlier ones ("Enter a number", "Required"), while the schema's own messages (for example the hysteresis one) are exactly the ones the backend sends. The backend still checks again; its 400 errors (for example `invalid cron expression`) are put in their field, and errors for a part without a field (for example `condition.kind` from an old backend that doesn't know `below-threshold` yet) are written above the **Save rule** button. Number fields read a decimal point (`2.5`); careful with a decimal comma: an English-language Chrome drops every comma, so `2,5` becomes `25` without an error message. The whole-number fields refuse `2.5` with "Enter a whole number (no decimals)". Write thousands without a separator (`1000`, not `1.000`, which the browser reads as 1). After saving or deleting, the screen moves to `/rules` with `replace`, so **Back** doesn't open the old form again.
- Every rule created, changed, or deleted from any dashboard makes an open `/rules` screen fetch its list again by itself (the `rule-changed` event).

## On-screen notices (toasts)

- They come from two sources: the results of your own actions (a failed command, a saved rule) and the backend's `event` events (a rule acting, a schedule running, a device disconnecting, offline mode, a command sent again). `rule-changed` doesn't become a toast.
- At most 2 at once (the third pushes the oldest out), each one disappears by itself after 4 seconds (`setTimeout`, not `setInterval`) or is closed with the ✕ button (44 × 44 px). Their region (`components/ToastRegion.tsx`) is mounted by `Layout` between the header and the screen content, so it is always there on every screen after logging in, with `role="status"` and `aria-live="polite"`: screen readers announce its content without moving the focus. The color always comes with an icon and text.
- Their place follows the screen width, so they don't cover the button being used. On screens of 1280 px and up: top right, in the empty space beside the content column, sticking to the top edge while the page scrolls. On phones and tablets (below 1280 px there's no empty space beside the content): at the BOTTOM of the screen, plus the height of the phone's system bar if there is one (`env(safe-area-inset-bottom)`). So that the lowest buttons (**Save rule**, **Delete rule**) can always be scrolled above the toasts, the page content gets 16rem of free space at the bottom (`pb-64` on `<main>`), and `scroll-pb-64` on `<html>` (`index.html`) makes a browser that scrolls by itself to a button or field (the Tab key, a field with an error) stop above the toasts. Tested at 375 px and 1280 px, light and dark, also with three toasts arriving at once: **Log out**, **+ New rule**, **Edit**, Lamp, Fan, the pump buttons, **Save rule**, **Cancel**, **Delete rule**, and **Yes, delete** are not covered. What can still happen on a phone: a button that happens to sit right at the bottom edge of the screen when a toast arrives is covered until the page is scrolled a little more (or the toast is closed with ✕, at most 4 seconds). On a short or very narrow screen (a phone turned sideways, or a phone 320 px wide) a toast can cover the Lamp/Fan row or the pump buttons, including a toast from the button just tapped. A tap that lands on a toast card doesn't reach the button under it: close the toast with ✕ first or wait until it goes away. The region's empty space (outside the cards) doesn't block taps.
- An event toast's color is taken from the data, not from its sentence: a device disconnecting (the device's status in the store isn't `online`), and a rule or schedule whose action wasn't carried out (`data.ok` `false` from backend 1.1, or `data.result` `no-ack`/`not-sent`) are red; the others are gray.
- Since v1.4 (Module 28): an `ota` event is green when an update **succeeded**, red for a rollback, failed, rejected, or expired, and gray when its command was accepted; `provisioning` (a new device through a claim code) is green; `revoked` gray; a device that **stopped on purpose** (`offline-mode`) is gray, not red. The `ota` event itself doesn't become a toast (the important steps already arrive as events), and an update command the device accepted gets no second toast from its HTTP answer.

## Logging out

The **Log out** button works in four steps: (1) it cuts the live connection first, (2) `POST /auth/logout` so the backend deletes the `HttpOnly` cookies (JavaScript can't delete them), (3) it clears EVERYTHING in the store and the toasts, so the next person in the same tab sees no leftover data or buttons of the previous account, (4) the route guard moves the screen to `/login`. If the **Back** button restores an old page whole from the browser's back/forward cache (it can happen when its address was typed straight into the address bar), `App.tsx` reloads that page (`pageshow` with `persisted`), so the previous account's content only shows for a moment and is then replaced by the Log in screen. If the server doesn't answer at Log out, the Log in screen says plainly that the session on the server hasn't been deleted. An expired session (or a logout in another tab) uses the same clearing, then writes "Your session has expired. Please log in again."

## Schema copies (`src/schemas/`)

`src/schemas/contract.ts` and `src/schemas/rule-basics.ts` are **identical copies** of `backend/src/schemas/` (explained in `src/schemas/README.md`). Since v1.4, `contract.ts` is data contract 1.6 (Module 28: `reset_reason`, `fw`, and the `ota` report in `vitals`; the `update` command; `intervals` in `config`). Don't change them in the frontend: change them in the backend, copy them again, then run `npm run check-schema` from this folder. The `check-schema.js` script compares the content of both files line by line (CRLF and LF line endings count as the same), prints `SAME` or `DIFF` with the first line that differs, and exits with code 1 if something differs. `src/schemas/login.ts` isn't a copy: the Log in form's schema is written by hand, mirroring `backend/src/routes/auth.ts`.

## Backend address (`.env.local`, optional)

Without any settings, the dashboard calls the backend at the page's host name + port `8080`: the page `http://localhost:5173` → API `http://localhost:8080`, and the page `http://<laptop-IP>:5173` on a phone → API `http://<laptop-IP>:8080`. The live connection (Socket.IO) uses the same address. If your backend is at another address, copy `.env.example` to `.env.local`, fill in `VITE_API_BASE` (for example `VITE_API_BASE=http://localhost:8081`), then restart `npm run dev`. `.env.local` doesn't go into Git, and for phone mode the `VITE_API_BASE` line must stay commented out with `#`. Every `VITE_…` variable is built into the JavaScript sent to the browser, so it only ever holds an address, **never** a secret. All of this is only for dev mode: the Docker web image always uses `/api` (built in at build time, see "How to run it with Docker Compose"), and `.env.local` doesn't go into the image.

## Opening it from a phone (home Wi-Fi)

**Home mode (Docker Compose, Module 26)** only needs the root `.env`: `WEB_ADDRESS=0.0.0.0` (the web counter opened to the home Wi-Fi, not only `127.0.0.1`) and the page's address on the phone added to `CORS_ORIGIN`, for example `http://localhost,http://127.0.0.1,http://<laptop-IP>` (with its port too if `PORT_WEB` isn't 80), then `docker compose up -d`. The phone opens `http://<laptop-IP>`, without port 5173. Put both lines back after trying it. Everything below (the settings and the steps) is for **dev mode** (Vite).

The phone and the laptop must be on the same home Wi-Fi (not a guest Wi-Fi). Turn on "phone mode" only while you try it, on a home Wi-Fi you trust, then switch back to "laptop mode". Since v1.0 an admin account can control devices from a phone: the admin password travels over plain `http://` (not encrypted yet, HTTPS follows in Module 27), so give a tester a temporary account and delete it afterwards.

| Setting | Laptop mode (default) | Phone mode (temporary) |
| :--- | :--- | :--- |
| `HOST` in `backend/.env` | `127.0.0.1` | `0.0.0.0` (not the Wi-Fi IP address: with an IP address, the backend stops serving `localhost`) |
| `CORS_ORIGIN` in `backend/.env` | `http://localhost:5173,http://127.0.0.1:5173` | plus `,http://<laptop-IP>:5173`. This one line applies to `fetch` (commands, saving and deleting rules included) and Socket.IO at once. Without it, a command from the phone is answered `403 request from the page http://<laptop-IP>:5173 refused` |
| Vite command | `npm run dev` | `npm run dev:phone` |
| Address in the browser | `http://localhost:5173` on the laptop | `http://<laptop-IP>:5173` on the phone |

1. Find the laptop's Wi-Fi IPv4 address: on Windows `ipconfig`, the `Wireless LAN adapter Wi-Fi` section; on macOS `ipconfig getifaddr en0`. Ignore the addresses of other adapters (vEthernet, Docker, VPN) that Vite also prints.
2. Change the two `backend/.env` lines above, then save (`npm run dev` in the backend restarts by itself). The database stays on `127.0.0.1`: it isn't opened to the Wi-Fi.
3. In this folder, run `npm run dev:phone`. If Windows asks, allow **Node.js JavaScript Runtime** only for **Private** networks.
4. On the phone, open `http://<laptop-IP>:8080/health` first (it must answer), then `http://<laptop-IP>:5173`, and log in. Logging in on the laptop doesn't carry over to the phone: a cookie belongs to a host name (`localhost` and the IP address are two different names).
5. When you're done trying, and always before the laptop goes to another network: put `HOST` and `CORS_ORIGIN` back, then start Vite again with `npm run dev`. The IP address may change tomorrow (the router hands it out again); if the phone can't open the page any more, find the IP again.

**Add to the home screen.** The dashboard can be made a shortcut on the phone's home screen (Chrome on Android: menu ⋮ → an install or shortcut option, for example **Install and create shortcut** → **Create shortcut**; iPhone: **Share** → **Add to Home Screen**). For the iPhone, `index.html` sets the icon `public/apple-touch-icon.png` (180 × 180 px: a simple line drawing of a house on a full light background, made by hand from an SVG) and the short name "Smart Home". Through `http://<laptop-IP>` this is only a shortcut, not an installed app: a Wi-Fi IP address isn't a secure address, so the browser doesn't install the service worker, and the shortcut breaks if the laptop's IP changes. A real app (PWA) exists since v1.3 through `https://` (Module 27): see the next section.

## A phone app (PWA, Module 27)

Since v1.3, `npm run build` (also inside `docker compose build web`) adds four files to `dist/`, all made by `vite-plugin-pwa` from the settings in [`vite.config.ts`](vite.config.ts):

| File in `dist/` | What it holds |
| :--- | :--- |
| `manifest.webmanifest` | the app's business card: the name "Mini Smart Home", the short name "Smart Home", the language `en`, the start address `/`, its own window without an address bar (`standalone`), the colors, and four icons. Its link (`<link rel="manifest">`) is added to `index.html` by itself |
| `sw.js` + `workbox-….js` | the service worker: keeps the dashboard's **shell** (HTML, JavaScript, CSS, icons; 10 files, ±1 MB) so that the app opens fast and stays open while the internet is down |
| `registerSW.js` | three small lines that install `sw.js` after the page has finished loading |

**What is kept and what isn't.** Only the shell. Every screen address (`/devices`, `/map`, `/devices/f00d00000001/history`, …) is answered with `index.html` from the store, then React Router picks the screen. Addresses that **aren't** dashboard screens always go on to the server and are never replaced by `index.html`: `/api/…` (the data and the live connection), `/grafana/…` (Grafana at the same address, Module 27), `/socket.io/…`, and (since v1.4) `/fw/…` (the devices' firmware downloads, Module 28). Without the `/grafana` exception, opening `https://iot…/grafana/` in a browser that has opened the dashboard before shows the dashboard's own "Page not found" screen, not Grafana (tried by the author). The home's data, readings, history, and map tiles are never stored: the numbers on screen always come from the server, so no stale number ever looks new.

**A secure address.** The browser only installs a service worker and offers to install the app at a secure address: `https://…` or `http://localhost`. So:

| Address | An installed app? |
| :--- | :--- |
| `http://localhost` (home mode, laptop) | yes, for trying it on the laptop (Chrome or Edge) |
| `https://iot.yourname.my.id` (a VPS or the Module 27 free path) | yes, on phones and laptops, from anywhere |
| `http://<laptop-IP>` or `http://<laptop-IP>:5173` (phone mode, home Wi-Fi) | no: only a shortcut (see above) |
| `http://localhost:5173` (`npm run dev`) | no: dev mode has no service worker |

**Installing.** Laptop (Chrome or Edge): open the address, then use the browser's app install menu (a button in the address bar or the ⋮ menu); the dashboard then opens in its own window with the house icon. Android phone (Chrome): open `https://iot.yourname.my.id`, then menu ⋮ → the app install option. iPhone (Safari): ⋯ → **Share** → **Add to Home Screen** (if it isn't there: **Edit Actions**) → turn on **Open as Web App** → **Add**. Chrome's menu labels on phones differ per version and language; installing on a real phone hasn't been tried by the author yet (see "Limits of v2.0").

**Checking on the laptop** (DevTools, F12): the **Application** tab → **Manifest** (name, icons, no errors) and **Service workers** (`sw.js` with the status *activated*). In the author's Chrome 156, `http://localhost` is reported as installable (no installability errors), the service worker is active on the first visit, and from the second visit on every screen is answered from its store.

**When the internet is down** (airplane mode, Wi-Fi off, or the server down): the installed app still opens and shows the **Log in** screen with the message `Can't reach the server. Check your internet connection, then try again.` Once connected again, open the app again (or reload); a login cookie that is still valid takes you straight back to the dashboard. Without a service worker, the browser's own error page shows.

**A new version.** The setting `registerType: 'autoUpdate'` makes a new service worker take over without asking, but it doesn't reload a page that is already open. After a new web image is deployed (rebuilt on the laptop, or since Module 29 pulled by the VPS and the Pi from GHCR): the **first** opening (or reload) still shows the old version from the store while the browser fetches the new one in the background; the **next** opening, after the browser has finished fetching that new version (usually a few seconds; longer on a slow phone network), shows the new version (tried by the author: the new version showed on the second reload, with no other step). An app on a phone that is only brought back from the recent-apps list doesn't necessarily check for a new version: close it, then open it again. Form fields being typed aren't lost by an update. Since v2.0, the number under the title (for example `v2.0.1`) shows the version on the screen, so you don't have to guess (tried by the author at `http://127.0.0.1` with headless Chrome 156: after the 2.0.1 build replaced 2.0.0, the first reload still showed `v2.0.0`, a page left open didn't change by itself, and the second reload showed `v2.0.1`, in the Indonesian edition's lab; this edition's lab saw the same two reloads on 6 November 2026, after 2.0.1 was deployed).

**Removing the service worker** (for example after `npm run preview`, or when you doubt the dashboard on screen is the newest version): DevTools → **Application** → **Storage** → **Clear site data**, then reload. This also deletes the login cookies at that address (you'll need to log in again).

**Icons.** `public/favicon.svg` (the tab icon, replacing Vite's lightning logo) is a line-drawn house with the same teal door as Module 24's `apple-touch-icon.png`, on a light tile with round corners. `pwa-64x64.png`, `pwa-192x192.png`, and `pwa-512x512.png` were made once by the author from `favicon.svg` (transparent corners); `maskable-icon-512x512.png` is a version with a full light background for Android launchers, which cut the icon into a circle or a rounded square: the house sits inside the 80% safe circle in the middle. All the PNGs are in the repo, so you don't need to make them yourself. `apple-touch-icon.png` (iPhone) stays the Module 24 file.

## Login and security

- The dashboard doesn't store passwords, tokens, or roles. The backend sets two `HttpOnly; SameSite=Strict` cookies: `access` (15 minutes, path `/`) and `session` (7 days, path `/auth`; through Caddy in home mode its path is rewritten to `/api/auth`). Over `https://` (Module 27, backend 1.4 with `TRUST_PROXY`), both are also `Secure`: the browser only sends them over an encrypted connection. The service worker never keeps `/api` answers, so the cookies and the account data aren't kept in its store either. JavaScript can't read them; the browser sends them because every `fetch` uses `credentials: "include"` and Socket.IO uses `withCredentials: true`. Nothing at all is stored in `localStorage`.
- If a request is answered with 401 (the `access` cookie has run out), `api.ts` calls `POST /auth/refresh` **once**, then repeats the request once. If the refresh fails too, the store is cleared and the screen moves to `/login`.
- Requests without a body (`POST /auth/logout`, `POST /auth/refresh`, `DELETE /rules/:id`) are sent WITHOUT the `Content-Type: application/json` header: the backend refuses a request that claims to carry JSON but whose body is empty (400).
- The server cuts the live connection every time the `access` cookie runs out (15 minutes) and at logout. The dashboard then calls refresh and reconnects by itself; if the refresh is refused (for example after a logout in another tab), the screen moves to `/login`. After 3 failures in a row the badge becomes **Disconnected**, and the page has to be reloaded once the backend is back.
- New data only comes through Socket.IO: there's no polling. `setInterval` is only used in `time.ts` for the clock on the screen. The Fleet screen only fetches its data again when there is news (tried by the author: 30 seconds idle on the Fleet screen = 0 requests).
- A claim code (Module 28) only lives in one component's memory until its box is closed: not in the store, not in `localStorage`, not in the page address. The database only stores its fingerprint.
- Firmware files are uploaded as raw content through the same `/api` (locked with the admin cookie); the dashboard never downloads firmware files. The `/fw/…` downloads are for devices only (the device key).
- Device names, rule names, and event sentences are shown as JSX text, which React escapes automatically; the dashboard doesn't use `dangerouslySetInnerHTML`.

## Limits of v2.0

- **The automatic tests only guard pure functions so far.** Five Vitest tests check the WIB time, the CSV, and the rule sentences. The screens, buttons, forms, the live connection, and the PWA aren't tested automatically yet (no jsdom or React Testing Library; end-to-end tests with Playwright are only an optional reading in Module 29). Changes to the look are still tried by hand, following the Module 16 pull request checklist.
- **The version on the screen = the version of the web image.** The backend version is read at `/api/health` (`"version"`). Both are the same as long as they're deployed from the same release; the dashboard doesn't compare them.
- **A new version shows after a reload** (the PWA, the same as v1.3–1.4): the number under the title only changes on the second reload.

- **The Fleet screen was tested with simulated devices, not boards.** The author tested the `/fleet` screen on the v1.4 web image + backend 1.5 with the simulator (`tools/device-simulator.js`, the firmware 1.7.0 design) and FAKE `.bin` files: upload (also the refusals in the browser and `409`), canary, one device, "Update all", a test release → rollback (±70 seconds), the vitals interval, a claim code → the new device showing by itself in ±1 second, deactivate, a viewer account, 375 px and 1280 px, light and dark. The timings on screen with a real ESP32 over Wi-Fi, and firmware 1.7.0 itself, haven't been tested.
- **Health isn't live per vitals.** The signal, RAM, and uptime numbers are fetched when the screen opens and when there is news (an update finished, a new device, the connection back); the time of their vitals is written on the card. "Uptime" is the number at the moment those vitals were sent, it doesn't count up by itself.
- **The program shelves (app0/app1) aren't shown**: contract 1.6 doesn't report them (only Serial and the OLED, the Module 28 Challenge).
- **Withdrawing a release has no button yet.** A bad release is withdrawn through Bruno (the request `withdraw test release`, `POST /firmware/node1/<version>/withdraw`); the Fleet screen then shows the **withdrawn** badge and no longer offers it.
- **Uploading has no progress bar and no time limit**: while uploading, its button says "Uploading…" (a stuck network = still "Uploading…"). Uploading through Caddy at `https://` with a domain name and a stand-in certificate was tried by the author (the Chrome form and `curl`, a 1.2 MB fake file); real Let's Encrypt wasn't.
- **The version right after "succeeded".** The version field is updated by the `GET /fleet` fetch the `succeeded` notice triggers; over HTTPS in the author's lab, the word **succeeded** sometimes showed before its new version (at most until that fetch finishes or the next `telemetry`, ≤ 10 seconds).
- **Fetches aren't merged.** Every finished update triggers `GET /fleet` + `GET /firmware` on every open dashboard: "Update all" for N devices = 2N requests per dashboard within a few seconds (N = 18 in the author's lab without problems; N = 100 not measured yet).
- **The file checks in the browser are only a helper.** A `<sketch>.bootloader.bin` file also starts with `0xE9`; the browser refuses it by its name, not by its content. What decides is still the backend (and HTTPUpdate on the device).

- **At home, still plain `http://`.** Phone mode (home Wi-Fi) opens the dashboard without encryption; passwords (the admin password too) travel in the clear. From the internet, the dashboard is opened over `https://` (Module 27: a VPS, or a Pi + Cloudflare Tunnel). HTTPS needs a domain name, so an IP address on the home Wi-Fi stays HTTP.
- **The installed app is only a shell.** Without the internet, the app opens but shows no numbers at all (no offline data), can't control devices, and sends no push notifications; alerts still come through Telegram (Modules 19, 25). A command tapped while disconnected isn't kept to be sent later.
- **A new version shows on the next opening** after the web image is rebuilt and the browser has finished fetching it in the background (see "A phone app"), not at once as in v1.2. Usually opening it again, or reloading twice a few seconds apart, is enough.
- **`npm run preview` leaves a service worker behind** at `http://localhost:5173`; a later `npm run dev` shows the old build until the site data is cleared (DevTools → **Application** → **Storage** → **Clear site data**). Tried by the author.
- **Installing on a phone hasn't been tried by the author yet.** What was tested: headless Chrome 156 on a Raspberry Pi (the manifest without errors, installable, the service worker active, the offline shell, a version update) at `http://localhost`, and at `https://` with a domain name and a stand-in certificate (in the lab, a simulated VPS and a stand-in for Let's Encrypt; this included Grafana `/grafana/` with the service worker active). Chrome Android's install button, the icon in a phone launcher, and iPhone Safari haven't been tried; the menu labels are written from documentation.
- **The web image is built for one API prefix, `/api`.** That address is built into the JavaScript at build time; the Compose dashboard can't be pointed at a backend at another address without rebuilding the image. An image you build yourself is only for the processor type of your machine (arm64 on a Pi or an Apple silicon Mac, amd64 on most Windows laptops); the robot's image (Module 29) holds both under one tag, and every machine pulls the content that fits its processor.
- **The path of the `session` cookie is patched in Caddy** (`header_down`), not in the backend. If the cookie path in the backend ever changes, `caddy/Caddyfile` must change with it.
- **`VITE_API_BASE` may only be a path (`/api`) or an address without a path** (`http://localhost:8080`). A full address with a path, for example `http://localhost/api`, isn't supported by the live connection yet: Socket.IO reads the `/api` at its end as a *namespace*, so the badge never becomes **Live**.
- **The Compose dashboard on the laptop doesn't update itself.** On the laptop, changing the code means `docker compose build web` + `docker compose up -d web` (±1 minute on a Pi 5); to change it while watching the result, use dev mode (Vite). On the VPS and the Pi, since Module 29 a new version arrives by itself, but only after the pull request is merged, the robot is green, and the robot makes the release tag `v<version>`: the VPS is updated by the robot over SSH, and the Pi checks for a new tag by itself every ±15 minutes (the project root README).
- **Leaving buttons out isn't protection.** The role on the screen is only convenience; the backend's guard (403) is what guards. A changed role only shows after a reload or within 15 minutes.
- **Only some API answers are checked by Zod**: the command ack and the rule list. The other answers (devices, readings, history, fleet, releases, Socket.IO events) are still trusted through TypeScript types.
- **After a 504, the screen goes back to the reported state**, although the backend will still send a lamp or fan command again if it hears from the device within 2 minutes (backend 1.4; after that it won't); the dashboard doesn't show commands that are still pending.
- **The curtain has no button yet**, and a rule's schedule is entered as a 5-field cron text (with three ready-to-click examples), not with a time and day picker yet.
- **The summary history has only four quantities**: temperature (average, lowest, highest), air humidity, soil moisture, and light. Air pressure, battery, and the water tank only show on the live cards. The ranges follow the API's defaults: 1 hour (raw readings), 24 hours (per 15 minutes), and 7 days (per hour).
- **The 5-minute chart is only for devices that send every 10 seconds** (Node 1 and the simulator). Node 2 sends every 5 minutes, so its chart is seen on the history screen.
- **Messages missed while the connection is down aren't sent again by the server.** Once reconnected, the 5-minute chart is refilled from the database, the device list (and its statuses) is fetched again, and the cards get the last reading the backend remembers. After the backend restarts, the state of the lamp, fan, pump, and curtain only appears with the next message because it isn't stored in the database; until then the control buttons aren't shown.
- **The map needs the internet.** Tiles come from the OpenStreetMap server (free, without guarantees, can be blocked if overused). Without the internet, the map box is plain gray; the marker circles are still drawn. Tiles may not be downloaded in bulk or stored for offline use.
- **Map points don't move live.** A point changed by the admin shows after the **Map** menu is opened again; only the status color is live.
- **Markers can't be selected with the Tab key.** The map box itself can be focused with Tab and then moved with the arrow keys (Leaflet's default), but the marker circles and their popups only open with a click or a tap. The same content (name, status, last seen, details link) is on the **Devices** screen.
- **Map tiles stay light in dark mode**, and for one home the points are close together (a few meters, zoom 18): the map is most useful when devices are spread out (a garden, another house).
- **Dark mode follows the system setting** of the phone or laptop; there's no light/dark button yet.
- "Tidy on a phone" was checked with DevTools device mode (375 px wide, a phone held upright) and headless Chrome 412 px wide, and phone mode was tried by opening the laptop's Wi-Fi IP address from that laptop itself; use by another person on a real phone and the home-screen shortcut haven't been tried by the author yet. The web image and the Caddyfile were tested by the author on a Raspberry Pi 5 (Ubuntu 26.04 arm64, Docker Engine 29.1.3, Compose 2.40.3) with Chrome 156; HTTPS was tested with a domain name and a stand-in certificate issuer on the author's machine, not real Let's Encrypt; Docker Desktop on Windows and macOS hasn't been tried. Tailwind CSS v4 needs a fairly new browser (Chrome 111+, Safari 16.4+, Firefox 128+).
