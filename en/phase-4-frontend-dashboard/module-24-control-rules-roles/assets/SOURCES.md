# Sources & Image Credits — Module 24

A recap of all the images in this folder. The original curriculum diagrams are licensed **CC BY 4.0**, and their `.svg` files are included so they can be edited. The diagrams follow the dashboard v1.0 and backend 1.1 code of this module (`src/App.tsx`, `RequireLogin.tsx`, `Layout.tsx`, `AdminOnly.tsx`, `SwitchButton.tsx`, `PumpButton.tsx`, `ToastRegion.tsx`, `src/toast.ts`, `src/rules.ts`, `check-schema.js`; backend `src/auth/security.ts`, `src/schemas/rule-basics.ts`, `src/schemas/rules.ts`, `src/services/automation.ts`, `src/services/commands.ts`, `src/routes/rules.ts`) and the behavior the author retested against the real backend 1.1 (`mini-smart-home/backend`) and its database, with the lab's mock senders and broker: a mock keyed MQTT broker (not Mosquitto) checking the same password file and access list, the simulator `f00d00000001` (`tools/device-simulator.js` of this module), and a mock Node 1 (obedient, slow, silent, and refusing modes). What was tested: the command `POST /devices/:id/command` with the answers 200 (`ack.ok` true and false), 409, 504 with the server sending it again, and a network error; the guard `onRequest` (403 for a viewer); the route map and the route guards; form errors per field and 400 errors from the backend; the `below-threshold` watering rule with the simulator's `soil` and `tank`. The soil and sensor numbers, times, device names, and the laptop IP `192.168.1.10` in the diagrams are **examples**; the watering-rule chart is an illustration without a time scale. The mini screens in the diagrams are simplified (no menu or app colors, the On button drawn dark): the real dashboard screens are in the screenshots. The real Node 1 part (Serial `threshold 20`) is read from the firmware v1.6.0 code, **not yet tested by the author on a real board**. The user test by someone else on a real phone is only drawn as a way of working, **not as a test result**.

The screenshots come from the author's English lab of 26 October 2026, **on a Raspberry Pi 5 (Ubuntu 26.04 arm64) with headless Google Chrome 156 (`Chrome/156.0.8078.47`), not on Windows with Microsoft Edge like the Indonesian edition**: Chrome driven over the DevTools protocol, a fresh profile per scenario (the two people of the admin/viewer picture = two separate browser contexts with their own cookies), `--lang=en-US`, the time zone emulated as Asia/Jakarta (WIB), light theme, scale 2. The dashboard v1.0 and backend 1.1 with its TimescaleDB database are real, but the senders are lab programs: the simulator `f00d00000001`, a mock Node 1/Node 2 (a program imitating firmware v1.6.0, with a slowly drifting example temperature), and the mock keyed broker; the sensor numbers are examples. The accounts are the Module 20 ones, `admin@home.test` (Home Admin) and `viewer@home.test` (Home Guest); no password, cookie, key, or IP address appears in any picture, and no port either (headless Chrome has no address bar). The 375 px width is **DevTools device mode, not a real phone**. The rollback was made by blocking `*/command` with the DevTools protocol command `Network.setBlockedURLs`, the same thing the DevTools **Request conditions** drawer does (the drawer's menu was not clicked). The DevTools front-end (Elements, Styles, Color Picker) was opened in a separate window of the same headless browser. The Lighthouse reports carry a run warning about a slower CPU (it concerns the Performance score, not Accessibility); it is cropped out of the picture. A real phone, iOS, another person, and the real Node 1 were **not** tested by the author. The screenshots for Practices 2–8 come from the module's final code (after Practice 9): before Practice 9, the teal and the gray text on your screen are slightly lighter, and the **Rules** menu in the dashboard header only comes in Practice 7. All sources accessed October 2026.
